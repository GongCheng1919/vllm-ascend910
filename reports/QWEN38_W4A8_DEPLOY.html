⚠ 官方 W4A8 ‡ 为什么只能定性读

05官方 arm 是怎么来的，以及那两行 W8A8 该怎么读

主管方要看「跟官方实现同路对比」。没有官方 checkpoint，就合成描述文件 —— 但合成出来的官方 arm 和我们以为的「厂商出货版」不是一回事，这一节把差别说清。

模型侧事实：Qwen3.8-27B 没有厂商量化 checkpoint

ModelScope 实测：只有 Qwen/Qwen3.8-27B（BF16）和 GGUF； <org>/Qwen3.8-27B-W8A8 形状的 id 全部 404。 P10 早先写的「A2 上有官方 W8A8」是错的，实际两个 -native arm 都没有权重。 但 vllm-ascend 打算支持它：packed_modules_model_mapping 里 model_type "qwen3_5" 有条目。缺的只是标定权重 —— 而本矩阵所有 arm 都是 load_format=dummy，没有任何 arm 声称精度。 所以合成一份 quant_model_description.json（npu_ops/python/gen_vendor_quant_desc.py） 就够让 vLLM 分配 int8/int4 参数并派发厂商 kernel。

读法 1：官方 W8A8 那行 = 我们给的层配置 × 官方 per-channel 实现

「官方 W8A8」用的是我们的 339 层（含 down_proj），跑的是官方实现 —— 两件要分开说

层配置是我们的：合成文件刻意把层集合对齐我们的 339，比值才隔离出 GEMM。 官方实现本身是 per-channel，我们是 mid-group（按组取 scale）。

结果：吞吐其实差得不算太多 —— 我们的 W8A8 对官方 W8A8 是 0.92× / 0.91× （b=1/4），慢 8–9%，换来的是每输出通道内按组量化、误差粒度细得多。

读法 2：上一轮厂商自己都不敢把 down_proj 量化掉

0.13 / QwQ-32B 的官方 W8A8：down_proj 是没量化的 float

在 QwQ-32B（vllm-ascend 0.13）上，厂商官方 W8A8 的 所有 down_proj 都留在 FLOAT。那是他们的标定决策 —— 而 down_proj 恰好是 per-channel 最难压的地方（K 巨大、fan-in 极宽：QwQ 的 27648 / Qwen3.8 的 17408）。

我们这次自定义 config 就全量化了，包括 down_proj。 敢这么做靠的是粒度：mid-group 在通道内再分组取 scale，per-channel 做不到的精度它做得到。 ⇒ per-channel 全量化可能不能很好地保持模型性能，而我们的 midgroup 应该可以。

⚠ 这句话是论证，不是实测：本矩阵全是 dummy 权重、没有任何精度数字。 它的证据链是「厂商在 per-channel 下宁肯留 float 也不量化 down_proj」+ 「group 粒度误差小于 channel 粒度」。把这条转成实测是下一期的精度关（§08）。

⚠ 别把合成 arm 当成「厂商出货的那一版」

真实厂商版会在层集合上不同 —— QwQ 上他们把 down_proj 留在 FLOAT， 那是标定决策，合成文件复现不了。也就是说：表里官方 W8A8 的 339 全量化， 是一个比厂商自己敢发的更激进的版本 —— 官方实现 + 我们的激进层集合。 速度行可比（都是同一层集合上的 kernel 对比）；「厂商出货版到底多快、精度如何」不在本表里。

厂商原生 W4A8 在 Qwen3.8 上两次撞墙（都不是我们的代码）

  1. 不吃 3 维输入：vision 塔的 attn.qkv 传进 3-D x， AscendW4A8DynamicLinearMethod.apply 不做 flatten ⇒ AclNN_Parameter_Error(EZ1001): x's dim should be in range [2, 2]. actual is [3] （厂商自己的 W8A8_DYNAMIC 有对应的 squeeze，所以 W8A8 没事） ⇒ 只能把整个 vision 塔留 BF16，权重 18.20 GiB 比我们的 16.83 GiB 大。
  2. 进不了 FULL_DECODE_ONLY 图：'CompilerConfig' object has no attribute 'experimental_config'（torch_npu npugraph_ex ← vllm_ascend compiler_interface.patched_get_compiled_gm），而 bf16 与 W8A8_DYNAMIC 同配置编得过。绕法是 --additional-config '{"ascend_compilation_config": {"enable_npugraph_ex": false}}'。

⇒ 两条加起来：在 0.23.0 + torch_npu 2.10 上，厂商 W4A8 路径在 Qwen3.8-27B 这个多模态 + GDN 架构上是走不通的（3-D 输入直接报错、默认图后端编不过）。 这不是「慢」，是「跑不了」。我们的路径两条都不撞：MidGroupW4A8Linear 一开始就 flatten，kernel 也不经过 npugraph_ex 的那条特殊路径。

⚠ 同一个坑我们自己踩了一半：W8A8Linear.__call__ 原本直接把 x 喂给 npu_dynamic_quant，3-D x 会让 pertoken_scale 变成 2-D， aclnnQuantMatmulV5 报 EZ0013 ... must be 1D —— 64 层 W8A8 arm 第一次直接跑挂。QwQ 的每个 Linear 都是 2-D，这个 bug 藏了整整六期。 已按 MidGroupW4A8Linear 的做法改成先 flatten 再 reshape。

⚠ 一处必须更正的早期判断

「Qwen3.8 的形状比 QwQ 更适合我们」在 GEMM 层面是错的。同 session 对照： TP=1 是 1.49–1.50× vs QwQ 的 1.55–1.56×，低 2–4%（18 个点里 17 个同号，方向可信）。 原因是 FFN 变瘦：down 的 K 从 27648 降到 17408。

真正的优势在部署形态，不在算子比值：16.83 GiB 装得进一张卡 ⇒ TP=1 可用， 而 TP=1 是 1.50×、TP=4 只有 1.19×。这是部署论证，报告里必须这么写。

07工具链迁移

从 vllm-ascend 0.13.0 抬到 0.23.0（最新版），CANN 8.5 → 9.1.0。

不用升驱动

我们在容器里，/usr/local/Ascend/driver 是宿主机的只读 bind-mount， 驱动动不了。但结果是不需要动：

  • CANN 9.1.0 自报 compatible_version 含 V100R001C23， 正是本机 driver 25.5.1 的 Innerversion；
  • kernel 零改动 55/55 编过，check_ragged 67 PASS / 0 FAIL；
  • 三个 Qwen3.8 形状与 CANN 8.5 SNR / max err / sum 完全相同，逐位一致 （性能 +0.4% ~ +2.9%，在 lab 噪声地板 ±2.6% 附近）。

安装页写的 HDK 26.0.RC1 是「验证过的组合」，不是最低要求 —— 本机 driver 的 compatible_version 只列到 C23 却一直在跑 CANN 8.5.0 = C25， 这张表本来就是保守的。

引擎管道的两个非默认开关

0.23.0 默认把 engine core 放进独立进程，我们那条四层私有属性链和传 callable 的 RPC 全断。加两个环境变量后恢复：VLLM_ENABLE_V1_MULTIPROCESSING=0（强制 in-process，恢复 0.13.0 形态）与 VLLM_ALLOW_INSECURE_SERIALIZATION=1。 这条链已经被一个默认值的变化打断过一次，是整套接入里最脆的一环， 应当拆掉改走 apply_model / collective_rpc 公开 API。
