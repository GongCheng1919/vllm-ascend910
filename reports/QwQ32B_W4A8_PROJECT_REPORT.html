1.2 一句话机理：为什么 PP 行、TP 不行

W4A8-mg 的收益域是「小 M × 大 K」，TP 切 K 把 o_proj 切出了这个域。 把 o_proj 的 kernel 耗时拟成 固定开销 + K·斜率（P7 D2）：斜率比 0.60（M=16），理论值 0.5 —— 访存优势完好无损；塌掉的是固定开销（+2.5 µs）。交叉点 K* = 固定差 / 斜率差， M=16 时 K* = 1665。
⇒ PP 不切 K（o=5120、down=27648，两层都在收益域内）⇒ 2.0–2.2×； TP=4 把 o_proj 切到 K=1280 < K* ⇒ 跌出收益域（实测 1.066，输）。 这把「PP 行 TP 不行」从现象变成了机理。

2.5 两条方法学规矩（都由踩坑立下）

一、任何「X 比 Y 快/慢」的结论必须带 M 档。本课题里 weight-only / mid-group / per-channel 三条路的排序在 M 上会换位。消融同理：M=16 的消融不能说明 M=512（P4 §7.2，同一个单点外推错误犯了两次）。
二、每加一个修正项，配一个故意写错的负对照。没有负对照，「PASS 116 dB」只能证明两边一致，不能证明两边正确（P3 §3.4）。

2.6 其它口径

  • PP 主表固定「每卡层数」不是总层数：PP=1→L16 / PP=2→L32 / PP=4→L64，每 rank 权重占用一致（~14 GB）， PP=4 / L=64 就是真实的 64 层 QwQ-32B。方法有效性的正向证据：改成固定每卡层数后， BF16 的每层斜率变成 1071 / 1084 / 1117 µs（PP=1/2/4）——一个理论上应该是常数的量真的是常数。
  • P4 报的是每层斜率，不是端到端比值：跑 4 层与 16 层差分除以 12，扣掉每步 ~4.1 ms 固定开销 （大头是 lm_head 152064×5120 bf16 = 1.56 GB/解码步，不被任何 arm 接管，留在分母里会把所有比值往 1 拉）。 同一次测量：16 层端到端 1.19×、外推 64 层约 1.26×、每层斜率 1.32×。
  • 长上下文的解码与 prefill 必须分开测：step_us 的 warmup 与计时跑同一批 prompt 且 prefix caching 开着 ⇒ 计时那一跑复用前缀 KV、几乎不付 prefill，即使 plen=8192 也是纯解码量；prefill 由 --prefill-probe 用全新 prompt 的 max_tokens=1 单独测。
  • 环境固定 ASCEND_RT_VISIBLE_DEVICES 从 1 号卡起排（device 0 已挂死）。

3 · 方案：mid-group W4A8 是什么

3.1 量化定义

沿 K 方向把长度 K 切成 K/GK 个组，A 和 W 用同一组边界：

y[m,n] = Σ_g  as[m,g] · ws[n,g] · ( Σ_{k∈g} A_q[m,k] · W_q[n,k] )

A_q: [M,K] int8,  as: [M, K/GK] bf16     (per-token × per-group，动态)
W_q: [N,K] int4,  ws: [N, K/GK] bf16     (per-channel × per-group)

W 和 A 用同一种量化方案（而不是「A per-token + W mid-group」混搭）是刻意的：两侧在同一个边界 rescale， kernel 里只有一套冲刷逻辑。scale 一律 bf16 且先 round 到 bf16 再用它量化——kernel 里就是 bf16， 用 fp32 scale 做 fake quant 会系统性高估精度。

3.2 为什么必须做 MSD 拆分

kernel_operator_mm_impl.h:317 的 MmadCal 只接受两种整型组合： <int32,int8,int8> → mad 与 <int32,int4b_t,int4b_t> → mad_s4。 cube 没有 s8×s4 混合位宽指令。所以「A 8bit、W 4bit」只有两条路：把 W 升到 int8（访存收益归零，纯亏）， 或把 A 拆成两个 int4 平面走 mad_s4。

a = 16*h + l + 8,   h = a >> 4        ∈ [-8,7]
                    l = (a & 15) ^ 8  ∈ [-8,7]      # 对全部 256 个 int8 值精确，不需要 clamp

C[m,n] = 16·Σ h·w + Σ l·w + 8·Σ_k W[n,k]
                             └── w_ksum，权重侧一次性预处理，推理零成本

拆分沿「数值位」、分组沿 K，两者正交，所以 mid-group 不需要重新设计拆分——唯一的变化是 w_ksum 从 [N] 变成 [N, K/GK]。 MSD 拆分对精度零影响（int32 内精确累加），fake quant 按 int8 激活建模即可。

3.3 非对称权重（GK=1024 的救命项）

P1 实测非对称权重把 PPL 缺口从 +9.03% 收到 +3.56%（§7），代价是每组多一个激活行和：

y[m,n] = Σ_g as[g,m]·ws[g,n]·( 16·S_hi + S_lo + 8·w_ksum[g,n] − wz[g,n]·a_ksum[g,m] )
两个容易写错、且不会报错的地方： （1）w_ksum 不减零点——它来自 MSD 的 +8 偏置，与非对称无关；零点走独立的 wz·a_ksum 项。 两者形状相同、来源无关，混用只掉 SNR 不报错。 （2）a_ksum 必须是 int32，不能是 bf16——GK=1024 的行和达 ~1.3e5，bf16 的 8 位尾数会舍到 ~0.2%， 零点项与主项同量级，误差直接落到输出。对照：wz 留 bf16 是安全的（[-8,7] 的整数，bf16 精确）。 判据是「这个量能否被 bf16 精确表示」，不是「它是不是 scale 类的量」。

而非对称本身几乎不要钱：同协议 sym/asym A/B 在 decode 档 asym/sym = 1.002–1.006， 最贵的是 M=64 的 1.031（BATCH_G 32→21 所致，不是那条额外的向量指令）。非对称不是性能上的取舍点。

4.6 P5：六条优化路，只有一条有净收益

P5 对大 M 的分组冲刷税做了定向消融，结论是结构性代价：

  • 成本模型：按「冲刷次数 / 行数」收费，不按字节体积。调度类改动全部 ≤5%；窄化字节反而 +1.5~6.2%。
  • 删掉 Fixpipe 能整个抹掉大 M 的 mid-group 税 —— 但「删除 X 有帮助」≠「重叠 X 有帮助」， 调度修复与字节削减两条都只值 5% 以内。
  • 六条路只有 L2 分带（BAND_N_CFG）有净收益：prefill −2~4.6%，逐位一致，零成本，但至今未设默认。
  • 默认保持 int32 累加 / 下发（BF16_FLUSH_CFG 非逐位一致，禁止设默认）。

4.7 ragged-K：把 K % 1024 == 0 从契约里拿掉

原 TP 路线是 GK = 1024/TP（TP=2→512、TP=4→256），它数值上成立但性能上必死——正是 P0 那条代价曲线。 决定性旁证是 P6 自己的数据：列并行 eff@2 0.92–1.07、eff@4 0.77–1.06 几乎完美，列并行切 N， 字节照样按 TP 减少，唯一区别是 GK 没变。

不是「TP 缩放不了」，是「GK 缩小」缩放不了。⇒ 不缩 GK，让算子原生吃任意 K。底层问题底层解决。
G       = ceil(K / GK)
n_g     = min(GK, K - g*GK)          # 第 g 组真实元素数
n_g_pad = ceil(n_g / 64) * 64        # 补到一个 int4 cube fractal（C0 = 32 B = 64 元素）
offset  = g * ceil(GK / 64)

每组独立补齐 ⇒ 每组都从 fractal 边界开始、含整数个 fractal ⇒ kernel 里不需要掩码，也不依赖 Mmad 对非对齐 k 的未文档化行为。 补零是精确的不是近似的：补进去的 q_a = 0、q_w = 0，对 Mmad 贡献 0，对两个 rank-1 修正项也贡献 0 （因为这两个和是在补齐后的范围上求的），所以没有任何地方需要记录「真实元素数」。 QwQ-32B 在 TP=1..8 的全部八个行并行分片，补齐量都是 0——raggedness 全在组层级。

5.5 为什么货架上的 W4A8 会在 batch≥32 崩掉

厂商路径是 weight-only + group_size=128：反量化成 bf16 再算，激活的 int8 从不进 cube。

  • M=1 它几乎不吃亏（2.43× BF16）——解码档是带宽受限的，weight-only 照样只从 HBM 读 int4，反量化在片上。 它放弃的是算力收益，而 M=1 根本不缺算力。
  • batch≥32 它崩掉（0.73–0.92× BF16，比 BF16 还慢）——cube 成为瓶颈后它得按 bf16 算力算，还要多付反量化。

g128 不是它的疏忽而是它的约束：每 128 个元素就要冲刷一次 L0C 并施加组 scale，真 W4A8 的 cube 路径基本走不通。 这也正是我们把 GK 定到 1024 的原因。

5.6 P4 推翻的两个判断

  • 「自定义 transformer 层 / 算子融合是下一步」——被一个参数取代。原本的理由是压主机开销（每层 ~390 µs 空隙）， FULL_DECODE_ONLY 一个参数把它压到 ~19 µs（385.8 wall vs 367 device）。主机侧没有空间了， 算子融合只值 −21 µs/层。要重开必须给出新的、设备侧的理由。
  • 「补齐修掉后应到 1.5–1.8×」——错，实际 1.41×。预测基于「设备时间省 249 µs/层」， 但当时引擎是主机受限的（利用率 36%），省下的设备时间只变成了更多空闲。 拿设备时间推墙上时间，中间少了一步「设备是不是瓶颈」。判据：step_trace_time.csv 的 Computing vs Free。

§6.4.4 与 §4.8 不矛盾，是两件不同的事。 §6.4.4 说的是「W4A8 自己 的 TP 扩展有效」（Computing 减半）； §4.8 说的是「W4A8 相对 W8A8 的优势 在 K < K* 时消失」。两者都成立，且 1.16× 的成因至今未定量拆分 ——通信税 vs 算子低维度效率，两者指向完全相反的后续（P8 vs P7），探针 scripts/profile_p65_tp_split.sh 已备好但未跑。

6.4.5 TP=4 的 prefill：打平（推翻了 PP 上的 0.64–0.69×）

TP=4 prefill 五档 batch 全部是 ~0.97× vs BF16 / 0.90× vs 我们的 W8A8，长上下文轴 0.88–1.02×。 这与 PP 上一致地输 0.64–0.69× 直接冲突。推测是 chunked prefill 截断了有效 M（⇒ 每个 chunk 的 M 落回收益域）， 但未验证，当前是推测不是结论，已列入欠账。

7 · 内存：唯一一条不随工作点换位的收益

KV 容量直接换算成并发 × 上下文的上限。可是 §6.3 实测： batch ≥ 256 时我们的 W4A8 输给我们的 W8A8（0.86–0.91×）。 ⇒ 「能装下更多」和「跑得更快」在这个方案里是两个相反的方向。

正确的用法是用多出来的 KV 空间换更长的上下文——那里我们最强（8K 仍 2.05× BF16， 且是五条 arm 里劣化最小的 +9.6%），而不是换更大的 batch——那里我们输。 两种用法消耗的是同一份 KV 空间，收益方向却相反，部署时必须显式选一个。

7.5 本节的限定

  • 权重占用是按模型几何精确计算并与磁盘实测交叉验证的，可信。
  • KV 容量是推算值：未实测特定 gpu_memory_utilization 下 vLLM 真实分配的 KV 块数， 也未计入激活峰值与图捕获的显存。方向可信，绝对值需实测，已列入 §12 欠账。
  • KV cache 本身没有被量化——本项目只动 Linear 的 W 和 A。KV 量化是一条独立的、 与本方案正交的收益线，未做。

8.2 三条改变了方法学的发现

  • GK 不是杠杆，AWQ 也不是。GK 从 1024 缩到 128（组数 8 倍，按 P0 的代价表根本买不起）只赚回约 1/3 的缺口； AWQ 式逐通道缩放两个方向都只值 0.3–0.5 dB。归因：mid-group 对激活值钱（down_proj +8.5 dB），对 int4 权重几乎无效 （per-channel 13.8 dB → GK=128 只到 18.3 dB）。真正的杠杆是非对称权重：一次拿回 5.5 个百分点， 而 kernel 只多一个每组的激活行和（§3.3，且实测几乎免费）。 另：GK=512 非对称的反常（+6.04%，比 1024 的 +3.56% 还差）是真的，已复现。
  • SNR 三层判据（32/35/35 dB）在现成 QwQ-32B 上作废——连 w8a8 自己都过不了（T2 最差 9.40 dB）， 可它 PPL 无损。门禁改用 PPL / 任务评测、以 W8A8 为参照系；Tier1/2 保留为定位问题层的诊断工具。
  • 门禁数字必须在完整 test split 上取：8 窗口的子集系统性高估退化近一倍（+18.67% vs +9.03%）， 因为开头那段文本明显更容易。这是偏差不是方差，加重复次数救不了。

8.3 GPTQ：做完了，没有增益

逐列量化 + 逆 Hessian 误差补偿，128 窗口顺序标定（每层用已量化的前序层产出的激活）。 标定集上层输出 SNR +1.3 ~ +6.1 dB，但完整 split 的端到端 PPL： asym-GPTQ +4.98% 反而差于 RTN 的 +3.52%，测试集逐层 SNR 增益 ≈0（+0.03 dB）。用户决定暂缓 GPTQ。

⚠ 冒烟时（4 窗口）看到 +10~20 dB 是假的——8192 token 对 down_proj 的 K=27648 是秩亏 Hessian， 那是样本内过拟合。必须用 ≥128 窗口。

9.1 这条支线上踩到的、值得单独记住的坑

  • 没有跨设备 UVA：各 rank 的 data_ptr 数值相同，裸指针会静默读本地内存。必须 aclrtIpcMem* 并断言地址不同。
  • AscendC 运行期下标的指针数组只读到 element 0，无警告 ⇒ 必须展开。它伪装成「这个特性不支持」，而且「一次一个指针」仍然能过。
  • NPUGraph 的输入张量必须保活：重放读的是冻结地址；丢掉输入会静默减少被回收的内存，模仿出「图 vs 图」的假腐败。
  • MC2（厂商融合算子）单跑绿、进 vLLM 必死（两种图模式都挂），ret=4 是一次性首调用失败（重试即可）——但它不能拿来定价。
  • 多 rank 探针出问题时先怀疑自己的同步：一天里三次「平台故障」全是自己缺/多了 barrier；你为观察 bug 而加的同步本身会制造 bug。
  • 被 kill 的 vLLM worker 会毒掉 HCCL：孤儿 VLLM::Worker_TPn 占着卡，之后所有 run 死在 hcclCommInitRootInfoConfig error 7。

11 · 讨论：FSDP / CP 能不能救 prefill 与大规模？

观察的出发点：在四种并行里，TP 是唯一攻击 K 的那一个。而 §4.8 已经证明我们的收益域由 K > K* 界定。那么切 M 而保 K 的并行——FSDP（权重分片）与 CP（上下文并行）—— 在几何上正好避开了杀死 TP 的那个机制。这条值得认真算账，而不是凭直觉接受或否决。

11.2 成立的部分：它把「藏不住的通信」换成了「藏得住的通信」

这一点比几何论证更强，而且是我们自己实测过的。 §6.4 那 3632 µs 的 all-reduce 之所以致命，不只是它大，而是它 Overlapped = 0； 而我们单独测过 all-reduce 是纯延迟受限的：10 KB 与 640 KB 一个价 ⇒ 这类通信在结构上无法用分块流水藏住，切分只会更糟（这正是自研 all-reduce 选择「消掉它」而非「切分它」的原因）。

FSDP 的 all-gather 完全不同：world=4 时每层要搬 185.7 MB，牢牢在带宽区 ⇒ 预取下一层权重真的能与本层计算重叠，而且双缓冲只需 2 × 248 MB，在 64 GB 上可以忽略。 FSDP 针对的正是杀死 TP 的那个机制。
还有一条 W4A8 独有的协同，本项目此前从未写下。 FSDP 的通信量正比于权重字节。int4 让它比 BF16 FSDP 小 4 倍： 15.85 GB vs 62 GB（每次前向、全模型）。 ⇒ 量化在这里不只是省显存，它直接把这套并行方案的通信成本降了 4 倍—— 换句话说，W4A8 让原本不划算的 FSDP 变得可能划算。这是「小模型权重」的一个二阶收益， 与 §7 的容量收益是同一个来源、不同的兑现方式。

11.4 不成立的部分：它救不了 prefill 的 GEMM

几何方向对，但幅度不够。prefill 的 M 是几千；world=4 除下来仍是两千多， 远在 M=512 之上——而 §4.8 在 M=512 实测的斜率比是 1.00： MSD 两遍 Mmad × int4 Cube 2× 速率 = 与一遍 int8 完全相等。 这是算术恒等，不是实现缺陷，再叠上 +16.8 µs 的固定开销必输。

要重新进入收益域需要每 rank 的 M 降到 ~128 量级，那意味着 world ≈ 数十，不现实。
⇒ FSDP 能让 W4A8 的 prefill「打平」，不能让它「赢」。它的收益要记在容量与通信账上， 不能记在 GEMM 账上。
而 decode 完全不能用 FSDP。M = batch 时每层计算约 0.3 ms， 而 all-gather 是 9.24 ms ⇒ 暴露约 30 倍，无论怎么预取都藏不住。 FSDP 是纯 prefill / 大 chunk 方案。

11.5 CP 的定位不同，值得单独看

CP 切序列（M），权重不动 ⇒ GEMM 侧零集合通信，只有 attention 需要 KV 的 ring 交换。 它是唯一能让我们的算子保持 TP=1 特性的多卡方案——K、N 都不变，没有 all-gather 要藏。 代价是它不降低每卡权重内存，所以不解决容量问题，需要与 PP 或 FSDP 组合。

11.6 建议

FSDP / CP 值得做原型验证，但要把预期定对： 收益是「容量 + 通信可隐藏性」，不是「GEMM 加速」。

它加强而不是替代 §9 的部署结论：prefill 走 W8A8 （或 per-channel W4A8——§4.5 实测它在 M=1024 仍赢 W8A8 1.12×，因为它没有分组冲刷； 代价是要多存一份 int4 权重，但那仍只有 15.6 GB），decode 走 mid-group W4A8。

验证顺序建议：先做 §12 的 profile split（它能告诉我们通信在总账里到底占多少）， 再决定 FSDP 原型值不值得——如果连 TP 那笔通信都不是主要矛盾，FSDP 的通信优势也就不值钱。
本节的证据等级：ring 带宽（11.31 / 20.14 GB/s）、权重字节、 每行计算成本（4.03 µs/行/层）均为实测；盈亏平衡点 9.2K / 16.3K tokens 是推算， 未做原型，未计入 all-gather 的启动开销、内存分配抖动与 vLLM 调度器的实际 chunk 行为。 方向可信，数字待验。

14 · 结语

执行侧：mid-group W4A8 从「910B4 到底有没有 INT4 cube」这个怀疑出发，走完了 INT4 cube 验证 → MSD 拆分 → mid-group 流水 → 非对称 → ragged-K → 打包成 torch 算子 → 在真 vLLM 引擎里被 ACL 图捕获、replay、四种投影全部接管、端到端生成， 数值上有逐位/逐字节/负对照三级门禁把关，PP=4 上跑通了真实的 64 层 QwQ-32B。

性能侧：在「小 M × 大 K × 不切 K 的并行形态」这个被机理解释清楚的区间里，方案是成立的 ——PP=4 解码对 BF16 2.0–2.2×、对我们自己的 W8A8 约 1.1×、8K 长上下文仍 2.05× 且劣化最小。 区间之外它一致地输：prefill（斜率比归零）、高并发（固定开销随 M 涨）、TP 切 K（K < K*）。 这三处不是三个 bug，是同一笔固定开销在三个方向上的投影，靶子已经量化成一个数字：把 M=16 的 K* 从 1665 压到 1280 以下。

内存侧：这是唯一一条不随工作点换位的收益——权重 62 GB → 19 GB（3.5×），计算值与磁盘实测互相验证，分组量化的元数据开销仅 1.3%。64 GB 单卡上 BF16 装不下而 W4A8 装下且余 41.6 GB，KV 容量 1.6× vs 我们的 W8A8。这是能力差异而非速度差异；且它让 FSDP 这类流量正比于权重字节的并行方案通信成本直接降 4 倍（§11）。但要注意它与延迟收益不指向同一个工作点：多出来的 KV 空间应当用来换更长上下文（我们最强）而非更大 batch（我们输）。

可用性侧：还不能宣称。权重是随机的，P2 的任务门禁没过，重复性门禁没做。 这三件事和性能优化正交，可以并行推进，但在它们完成之前，本报告里的每一个数字都只是延迟数字。
