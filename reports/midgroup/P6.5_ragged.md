# Ragged-K:让 mid-group W4A8 接受任意 K

**2026-08-17 · 单算子层已完成并验证 · 引擎层未测**

---

## 一句话

把 `K % 1024 == 0` 这条约束从算子契约里彻底拿掉之后，**行并行投影第一次真的随 TP 缩放**
（eff@4 从 0.25 → 0.54），对普通 W8A8 的比值在解码档从 P6 的 1.13–1.83 变成 **0.62–0.84**，
而**对齐形状零退化**（≤2.1%，在噪声地板内）、**精度等于 P2 签核的那个配置**（+0.05 dB）。

---

## 1. 为什么要动契约

原 TP 路线是 `GK = 1024/TP`（TP=2→GK=512、TP=4→GK=256）。它数值上成立，但性能上必死：
`P0_COST.md` §5 在**固定 K、只变 GK** 的对照里早就量过 —— GK=512 是 1.54–2.57× pc、
GK=256 是 2.4–4.1× pc，P0 的判词是"512 约打平、256 出局"。

P6 测到的行并行停滞（`mg/w8` 从 0.84 翻到 1.20/1.45/3.77）**就是 P0 那条代价曲线在
TP 强迫的 GK 上取值**，不是新现象。决定性旁证是 P6 自己的数据：**列并行 eff@2 0.92–1.07、
eff@4 0.77–1.06 几乎完美** —— 列并行切 N，字节照样按 TP 减少，唯一区别是 **GK 没变**。

> 不是"TP 缩放不了"，是**"GK 缩小"缩放不了**。

所以路线定为：**不缩 GK，让算子原生吃任意 K。** 底层问题底层解决，不把底层约束推给上层
找补。附带效果是这套算子从"给 QwQ-32B 定做"变成通用算子。

## 2. 契约

**对外：M、N、K 任意**（K=1057、奇数 K、末组只有 1 个元素都要过）。
**对内：每个量化组补零到一个 int4 cube fractal（C0 = 32 B = 64 元素）。**

```
G       = ceil(K / GK)
n_g     = min(GK, K - g*GK)          // 第 g 组真实元素数
n_g_pad = ceil(n_g / 64) * 64        // 补到 fractal
offset  = g * ceil(GK / 64)          // 组起点，对每个 g 都成立
```

每组独立补齐 ⇒ 每组都从 fractal 边界开始、含整数个 fractal ⇒ kernel 里不需要掩码，
也不依赖 Mmad 对非对齐 k 的未文档化行为。

**补零是精确的，不是近似的。** 补进去的 `q_a = 0`、`q_w = 0`，所以它对 Mmad 贡献 0，
对两个 rank-1 修正项（`w_ksum = Σ q_w`、`a_ksum = −Σ q_a`）也贡献 0 ——
**因为这两个和是在补齐后的范围上求的，所以没有任何地方需要记录"真实元素数"**。
末组的 `scale = amax(|x|)/127` 也不受影响（补零不抬高绝对值的 max）。

QwQ-32B 在 **TP=1..8 的全部八个行并行分片，补齐量都是 0** —— raggedness 全在组层级。

| K_rank | TP | G | 末组 | 补齐 |
|--:|--:|--:|--:|--:|
| 5120 / 2560 / 1280 / 640 | 1/2/4/8 | 5/3/2/1 | 1024/512/256/640 | **0** |
| 27648 / 13824 / 6912 / 3456 | 1/2/4/8 | 27/14/7/4 | 1024/512/768/384 | **0** |
| 1057（病态）| — | 2 | 33 → 64 | +31 |
| 1025（病态）| — | 2 | **1** → 64 | +63 |

## 6. 三条必须一起读的边界

**(a) prefill 档（M=128/512）我们输给 W8A8，而且不是 ragged 造成的。**
`o/M=512/TP=1` 就已经是 **1.170** —— 那是 P0/P5 的大 M 结构性税，跟 TP、跟 ragged 都无关。
TP 只让它更明显（M=512：1.170 → 1.386 → 1.449）。这与 P6 D13 已发布的结论一致
（W4A8 是解码方案，prefill 输 0.64–0.69×），**部署形态仍然是 prefill/decode 分离**。

**(b) W8A8 在大 M 下超线性缩放，机制未定位。**
`down/M=512` 的 w8 是 618.29 → 234.66（2.63×，超过 2）。`--cold` 的轮换足以冲掉 L2
（int8 侧 15 × 70.8 MB = 1.06 GB > 168 MB），所以不是 harness 的 L2 假象。
按 P5 D6 的规矩**不给它编机制**，只记录"大 M 的比值里有未解释的成分",不拿它支撑结论。

**(c) TP=8 开始碰到新的上限。**
`o/M=128` 在 TP=8 是 27.75 µs，比 TP=4 的 26.74 **更慢**：K_rank=640 时几乎没有 K 活了,
每 tile 的固定开销（P5 的 dmaonly 地板）成了主项。这是下一个杠杆,不是这一轮的问题。

## 7. 精度：等于 P2 签核的那个配置

TP 下每个分片**独立量化**，所以 ragged 只**增加**组边界、不会变粗。用真实 QwQ-32B 权重
（3 层的 o_proj + down_proj）量的 fake-quant SNR：

| | TP=1 | TP=2 新 | TP=2 旧 | TP=4 新 | TP=4 旧 | TP=8 新 |
|---|--:|--:|--:|--:|--:|--:|
| 均值 dB | 15.89 | **15.93** | 16.74 | **16.12** | 17.73 | **16.45** |
| 相对 TP=1 | — | **+0.05** | +0.85 | **+0.23** | +1.84 | **+0.56** |

**新路线从不比 TP=1 差**，也就是**精度等于 P2 测过的那个配置**——这才是门禁关心的量。
旧路线（GK=1024/TP）确实更细、更好（+0.85 / +1.84 dB），**那是它用速度换来的精度**，
而它在速度上过不去（§5）。选路线时这两栏要一起看。

## 8. 路上抓到的四个坑

| # | 坑 | 为什么值得记 |
|---|---|---|
| 1 | **`DataCopyPad` 的 `isPad=false`** 会把 GM 里紧随其后的**真实数据**读进补齐区（66 字节请求搬 96 字节）| 症状极具误导性：`a_scale` **全过**（同分布多 15 个采样，amax 在 bf16 下常常不变），`a_ksum`/`a_hi`/`a_lo` 全错。**"amax 对、和错"直接指向多读了同分布数据**，而不是算错了 |
| 2 | **改 `.inc` 不触发 kernel 重编** —— `ascendc_library` 不追踪它 | 第一次修 ① "没生效"就是这个：编的只有 host，kernel 是旧的，于是**拿旧 kernel 出数**。已在 `build.sh` 里堵死 |
| 3 | harness 参考实现用 `M` 而非 `Mp` 取 `a_scale` 行距（既有 bug）| 只要 M 被补齐就全表 FAIL，看起来像 kernel 坏了。开工时把 ragged 的失败和 M 补齐的失败混在了一起。之所以活到今天：所有既有调用点恰好 `M % TILE_M == 0` |
| 4 | ragged 让**常量组**第一次可达，而 asym 量化器在那里是坏的 | `_tiny_where_zero` 把 scale 抬到 tiny，**但没管 zero**：`zero = qmin − round(mn/tiny)` ≈ 1e35，在 bf16 里还是有限值,一路传到 kernel 的 `wz*a_ksum` 才在 fp32 变 inf。**一个只护住公式一半的 guard,比没有 guard 更危险** |

第 ④ 条的修复已验证：非退化组（gl=1024/512/128/33）与修改前**逐位相同** ⇒ P2 的数字不受影响。
它也说明 **lab 门禁自己造的输入分布可能恰好绕过真实管线才会踩的退化情形**
（这里是 `w_zero` 是随机生成的而不是从数据算的），所以 torch 侧的 seam 测试不是重复劳动。

## 10. 引擎级 TP：计算减半了，但延迟没降

`sweep_p65_tp_engine.sh`，L=16、batch=1、`FULL_DECODE_ONLY`，step µs：

| arm | TP=1 | TP=2 | TP=4 | TP1→4 |
|---|--:|--:|--:|--:|
| BF16 | 20868 | 14506 | 12690 | **1.64×** |
| 我们 W8A8 | 12246 | 11959 | 11842 | 1.03× |
| 我们 W4A8 | 10045 | 10808 | **11589** | **0.87×** |

方向在 6 个测点上一致（TP=2 是 0.93/0.88/0.90，TP=4 是 0.87/0.87/0.84 @batch 1/16/64）。
对 BF16 的领先从 2.08× 塌到 1.09×。

### 账逐项对得上（`step_trace_time.csv`，µs/step，profiling 开着）

| | Computing | Comm（未重叠）| **Overlapped** | Free | Stage |
|---|--:|--:|--:|--:|--:|
| TP=1 | 6751 | 0 | 0 | 5302 | 12053 |
| TP=4 | 3275 | 3632 | **0** | 5976 | 12882 |

1. **计算确实减半**（2.06×）。lab 预测 GEMM 省 2770 µs，实测 Computing 省 3476 µs，
   多出的 ~700 µs 是注意力头也随 TP 切了 —— 两边独立吻合。**kernel 侧兑现了。**
2. **`Overlapped = 0`**：collective 一微秒都没和计算重叠。
3. **Free 那 5.3 ms 没动**（TP=1 就有，331 µs/层）。

省 3476 − 加 3632 − 空闲涨 674 = **+829 µs**，与实测 12053 → 12882 **完全相等**。

### 排除掉的三个「是不是我们没做对」

| 假设 | 判定 | 依据 |
|---|---|---|
| 我们的 op 进不了 ACL graph | ❌ | `--eager` 31003 vs graph 10045 µs = **3.09×** |
| 那笔开销在 host 侧 | ❌ | profile 里它是 `Communication` 和 `Free`，都是设备侧 |
| BF16 走了 matmul-allreduce 融合而我们没走 | ❌ | 该开关默认 `'0'`，**对所有 arm 都关着** |
| TP=4 用了跨拓扑组的设备（1,2,3,4）| ⚠ **只对解码无关** | 10 KB 上换 2,3,4,5 一样；**2560 KB 上差 1.29×**（6.92 vs 8.94 GB/s）|

> **这一行我第一版写成了「❌ 排除」，是错的。** 那两组设备**都是跨组的**（边界在
> logic 3/4），我拿两个落在同一侧的配置去否证一个区分；而 2560 KB 那一行的 1.29×
> 差异被我当噪声扔了。

### 组内 vs 跨组：1.78×（TP=2 干净对照）

TP=4 做不到这个对照 —— device 0 挂死，组内凑不出 4 张卡。10240 KB / ring 带宽：

| 设备 | 组关系 | 10 MB | ring 带宽 |
|---|---|--:|--:|
| 1,2 | 组内 {0–3} | 927 µs | 11.31 GB/s |
| 2,3 | 组内 {0–3} | 927 µs | 11.31 GB/s |
| 4,5 | 组内 {4–7} | 928 µs | 11.30 GB/s |
| **3,4** | **跨组** | **521 µs** | **20.14 GB/s** |

三个组内配置落在 11.30–11.31 GB/s，唯一跨组的是 **1.78×** —— 两组各四卡、各有自己的
带宽域，跨组的 ring 同时吃两组。**逻辑分组确认为 {0,1,2,3} / {4,5,6,7}。**
10 KB 上四种配置都是 ~175 µs。

**这条打在我们最弱的环节上。** 行并行的 all-reduce 是 `[M, hidden]`，**prefill 的 M
是几千**（M=2048 → 20 MB，牢牢在带宽区），而 §6(a) 说的正是 prefill 我们输 0.64–0.69×。

| 场景 | payload | 选卡是否有用 |
|---|---|---|
| 解码 batch=1 | 10 KB | ❌ 延迟受限，四种配置一样 |
| prefill / 大 batch | ≥2.5 MB | ✅ **均衡跨组值 1.78×** |

TP=4 的具体建议：用 `2,3,4,5`（2+2）而不是 `1,2,3,4`（3+1），2560 KB 上 1.29×。

### all-reduce 是纯延迟受限的 —— 这决定融合要怎么做

`bench_allreduce.py`，4 rank：

| payload | devs 1,2,3,4 | devs 2,3,4,5 |
|--:|--:|--:|
| 10 KB | 258 µs | 271 µs |
| 640 KB | 268 µs | 265 µs |

**字节 ×64，时间 ×1.03。** 贵的不是线，是**每次调用的固定开销**。所以：

- ❌ **分块流水**（沿 N 切块、块间重叠，`npu_mm_all_reduce_base` 的做法）在这台机器上
  **更糟** —— 每块都付满 ~113 µs，切 4 块把通信从 113 变成 452 µs。而且 batch=1 解码
  层内是严格串行链，**没有独立工作可以藏**。
- ✅ **消掉那次调用**：一个 fused op，让 GEMM 在 epilogue 里直接做跨 rank 归约。
  先例是 CANN 自己的 `npu_mm_all_reduce_base`（matmul+all-reduce 单 op），
  说明跨设备原语存在。天花板 **1.30×**。

## 11. 那 5 ms 空闲：查清了，而且一个开关拿回 1.23×

### 不是图被切碎（我先前的推断是错的）

| gap 大小 | 个数 | 占空闲 |
|---|--:|--:|
| <10 µs | 12697 | **4.0%** |
| >200 µs | 370 | **84.5%** |

图被切碎应该是 ~1000 个 ~330 µs 的 gap。实际一个中位步（257 kernel，
span 10786 = busy 6735 + idle 4050 µs）里 **5 个 gap 占 91%**：

| gap | 之后紧跟的 kernel | 是什么 |
|--:|---|---|
| **1889 µs** | `aclnnInplaceFillScalar_Fill` | 填输入缓冲 |
| 653 µs | `aclnnInplaceFillScalar_Fill` | 同上 |
| 490 µs | `FusedInferAttentionScore` | 注意力前 |
| 444 / 209 µs | `aclnnIndexSelect_GatherV3` | 取 block table |

全是 vLLM 的 scheduler / 输入准备，**在模型 forward 之前**。

### 空闲与 arm 无关 —— 三点确认

| arm | Computing | Free | step | Free 占比 |
|---|--:|--:|--:|--:|
| BF16 | 17806 | 4703 | 22626 | 21% |
| 我们 W8A8 | 9006 | 5021 | — | — |
| 我们 W4A8 | 6751 | 5302 | 12053 | **44%** |

绝对值一样、占比差一倍 ⇒ **引擎每步的固定 host 开销，不是我们引入的**。
正确表述：**我们把计算做快了 2.6×，于是引擎的固定成本变成了 step 的 44%** ——
这是"跑得太快"的问题。

### `--async-scheduling`：一个开关，1.23–1.29×

vLLM 的 `SchedulerConfig.async_scheduling` 默认 **关**，作用是把 host 准备与上一步的
forward 重叠：

| arm | batch | async 关 | async 开 | 加速 |
|---|--:|--:|--:|--:|
| **我们 W4A8** | 1 | 10045 | **8182** | **1.23×** |
| **我们 W4A8** | 16 | 12124 | **9430** | **1.29×** |
| BF16 | 1 | 20868 | 18687 | 1.12× |
| BF16 | 16 | 24850 | 21634 | 1.15× |

零代码、零 kernel 改动，而且**帮我们比帮 BF16 多**（空闲在我们 step 里占比更大）。
**对 BF16 的领先从 2.08× 涨到 2.28×。** 3.3 ms 空闲里 async 吃掉约 1.9 ms，
剩 ~1.4 ms 重叠不掉。

> ⚠ **`async_scheduling` 不支持 PP** —— P6 那条已交付的 PP 路线用不了它。
> 这是 PP 与 TP 之间新增的一条不对称，选部署形态时要算进去。

### 两条限定

- **profiling 放大 host 时间**：未开 profile 空闲是 3.3 ms（33%），开着 5.3 ms（44%）。
- **L=16 系统性放大占比**：空闲是每步固定的、不随层数长，真实 64 层设备活儿 4 倍
  而空闲不变 ⇒ 占比降到约 **17%**。所以 async 的收益在真实模型上会小于 1.23×。
  （TP 那笔交易两边都随 L 线性，所以 §10 的 TP 结论在 L=64 不变。）

### async 开着之后，TP 变成精确打平 —— §10 那笔账的独立验证

| w4a8, async 开 | TP=1 | TP=4 |
|---|--:|--:|
| batch=1 | 8182 | **8217（1.00×）** |
| batch=16 | 9430 | 11102（0.85×）|

**去掉 idle 项之后，TP=4 与 TP=1 完全相等**（差 35 µs = 0.4%）。而 §10 的分解预测的
就是 (GEMM 省 3476) − (通信加 3632) = **+156 µs ≈ 0** —— 两个数都在噪声内，
**用完全不同的方法算出同一个 0**。

**这让 fused op 的定性变了**：TP 现在不是"亏"，是**精确打平**，而挡在"打平"与
"TP 真的有用"之间的就是那 3632 µs 通信。消掉它 ⇒ 8217 − 3632 ≈ 4.6 ms ⇒
**对 TP=1 是 1.78×**（不是先前估的 1.30×，因为基线已被 async 压低）。
**fused GEMM+all-reduce 从"挽回亏损"升级成"TP 能不能用的唯一开关"。**

### 下一步，按收益排序

| # | 事项 | 收益 | 状态 |
|---|---|--:|---|
| 1 | `--async-scheduling` | **1.23–1.29×** | ✅ 已验，一个开关 |
| 2 | **fused GEMM + all-reduce** | **1.78×**（TP=4 对 TP=1）| ⛔ **被 MC2 阻塞** —— 见下 |

## 12. fused op 开工调研：原语齐全，但 MC2 在这台机器上跑不起来

按"不猜先探"的规矩，开工第一步是查原语和定价，不是写 kernel。三个结果：

**(1) in-kernel HCCL 原语存在，而且比预想的强。**
`$CANN/aarch64-linux/asc/include/adv_api/hccl/hccl.h` 的 `class Hccl`：
`AllReduce` + **`Commit` / `Wait` 解耦**（所以能真重叠），
而且有 **`GetWindowsInAddr(rankId)`** —— "shared by all ranks in the same comm
group"，即**内核内直接访问对端显存**。于是两条设计，第二条才贴合 §10 的测量：

| | 做法 | 10 KB 上的预期 |
|---|---|---|
| A | `Hccl::AllReduce` + `Commit`/`Wait` | 省掉 op launch，仍走 task/msg 机制 |
| **B** | `GetWindowsInAddr` + `QueueBarrier` + 自己在 AIV 里归约 | **完全没有 HCCL task**，成本只剩 barrier |

（`AllReduce` 还有 `repeat>1`，那正是**分块流水**的接口 —— 显式不用。）

**(2) host 侧的 context 不用自己造。** `npu_mm_all_reduce_base(x1, x2, str hcom, ...)`
的通信域就是一个**字符串 comm name**，
`pg._get_backend(torch.device("npu")).get_hccl_comm_name(rank)` 一行拿到。

**(3) ⛔ 但 MC2 跑不起来。** 本想用 CANN 自带的融合算子给我们的项目定价（不写一行
kernel），4 rank 上必然失败：

```
aclnnQuantMatmulAllReduceV2 failed, error code is 561000
Nnopbase fails to invoke the HcclAllocComResourceByTiling ... ret = 4
```

`HCCL_BUFFSIZE=200`、`HCCL_OP_EXPANSION_MODE=AIV` 都不解决。

**为什么这个负面结果值钱**：我们自研的 `Hccl::InitV2` 会走**同一条**
`HcclAllocComResource` 路径，所以这个阻塞会原样挡住我们。**在一个下午发现它，
比写三天 AscendC 之后发现强得多。**

⇒ **fused op 的第一个任务不是写 kernel，是让这台机器上跑通任何一个 MC2 算子。**
通了之后立刻用 `bench_fused_allreduce.py` 给融合定价，那个数决定后面值不值得投入。
