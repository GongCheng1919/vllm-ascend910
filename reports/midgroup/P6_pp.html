1. 一句话结论

PP 是今天就能部署的那条并行，我们的 W4A8 在它下面一点没掉——真实 64 层 QwQ-32B 跑 PP=4，解码对 BF16 2.0–2.2×，且长上下文下最稳（8192 上下文仍 2.05×，是五条 arm 里衰减最小的）。

但有两条硬边界，必须写进部署方案：

  1. PP 给容量，不给延迟（§3.4）。token 仍要串行穿过全部 64 层。
  2. prefill 我们是输的（§5.2）：我们的 W4A8 prefill 只有我们 W8A8 的

0.64–0.69×，对 BF16 也只有 1.09–1.20×。W4A8 是解码方案，不是 prefill 方案。

---

2. 口径——先读这一节

2.1 为什么固定「每卡层数」而不是总层数

PP 按层切。若固定总层数，PP=4 只剩 4 层/卡，每步被流水开销主导，GEMM—— 唯一被我们改变的东西——只占一小块，五条 arm 会假性收敛。

更糟的是它破坏两点斜率法：固定总层数那一轮读出 BF16 在 PP=4 的每层斜率 310 µs、PP=1 是 1048 µs，等于「开 PP 让一层便宜了 3.4 倍」，结构上不可能。

本报告主表一律 16 层/卡：PP=1→L16、PP=2→L32、PP=4→L64， 每 rank 权重占用一致（~14 GB）。PP=4 / L=64 就是真实的 64 层 QwQ-32B。

方法有效性的正向证据：改成固定每卡层数后，BF16 的每层斜率变成

1071 / 1084 / 1117 µs（PP=1/2/4）——一个理论上应该是常数的量真的是常数。

2.2 五条 arm 分别是什么，以及它们并不对等

arm权重来源量化覆盖的层
bf16models/QwQ-32B无—
w8a8-nativemodels/QwQ-32B-W8A8vllm-ascend缺 down_proj
w4a8-nativemodels/QwQ-32B-W4A8-Randomvllm-ascend四种投影
w8a8（我们）同 models/QwQ-32B 转换per-channel INT8 + per-token四种投影
w4a8（我们）同 models/QwQ-32B 转换mid-group GK=1024 非对称四种投影

两条关键限定：

  • w8a8-native 不是对等的 W8A8。 其 quant_model_description.json 把

全部 64 个 down_proj 标成 FLOAT，运行时证据吻合（每 rank 8 个 linear 中 6 个 AscendLinearMethod + 2 个 AscendUnquantizedLinearMethod）。 down_proj 是层内最大的 GEMM（K=27648）。**「我们的 W8A8 比原生快」主要来自 量化的层集不同，不是 kernel 更快**，不要当成 kernel 对比。

  • w4a8-native 是 weight-only：反量化成 bf16 再做矩阵乘，激活的 int8

从未进 cube（P4 D3）。它在大 batch 比 BF16 还慢是结构性的，不是"W4A8 慢"。

我们的 w8a8 / w4a8 这一对是**从同一份 BF16 权重、在同一个 process_weights_after_loading 钩子上、对同一组 64 个 linear** 转出来的，

只有这一对的比值干净地隔离了 GEMM。

2.3 重复性带宽 —— ±15%（最坏）

p6_pp_isorank*.csv 与 p6_pp_concurrency.csv 有 60 个重复测点：

量medianp90最坏
绝对 step_us1.8%7.2%15.0%
比值（各自轮内算完再跨轮比）3.1–5.2%—17.1%

比值并不能抵消漂移，两轮之间同一条比值最坏能差 17%。直接后果：

  • 小于 5% 的单点差异不作数。
  • 只有在多个 batch/PP/上下文上方向一致的模式才当结论。
  • 本报告的比值一律按两位有效数字读（"约 2.0×"，不是"2.08×"）。

2.4 每条 arm 都有主动查询的生效证据

不看日志有没有打印——日志的缺席不是证据（转换日志每 64 次才打一行， 父进程计数器在多 rank 下天然是 0；2026-08-15 的 PP=4 就是这么被当成 W4A8 测的， 实际全程 BF16）。本轮两道证据都是主动查询返回值：

  • collective_rpc 逐 rank 查转换数：PP=4/L=64 每 rank converted=64

（16 层 × 4 投影），任一 rank 为 0 直接拒绝出数。

  • apply_model 逐 rank 查每个 Linear 的 quant_method 类名——**这条对五条 arm

都生效**，包括我们不接管的两条 native。w8a8-native 的缺口就是这么发现的。

2.5 其它

  • 图模式必须显式给 FULL_DECODE_ONLY：同样的 kernel 在 vllm-ascend 默认的

PIECEWISE 下测出 1.41×、在 FULL_DECODE_ONLY 下 2.78×（P4 D10）。

  • step_us = 总时间 / out_len，out_len=64。
  • 每个配置跑一次（非 median-of-N），故有 §2.3 的带宽。

w4a8-native 在 batch≥64 比 BF16 还慢（0.78–0.87×），复现 P4 D3 的 weight-only 结构性问题。

3.3 优势不随 PP 衰减

我们 W4A8 对 BF16：PP=1 → 2 → 4 是 2.01 → 2.03 → 2.08（batch=1）。 考虑 §2.3 的带宽，正确读法是"跨 PP 持平，没有衰减"， 而不是"随 PP 变强"——后者的幅度落在噪声里。

我们 W4A8 对我们 W8A8：约 1.1×（1.05–1.22 跨全部 PP 和 batch≤64）。

3.4 PP 给的是容量，不是延迟

吞吐 tok/s @16 层/卡（只能同 PP 内横比——跨 PP 是不同大小的模型）：

一个 token 仍要串行穿过全部 64 层，PP 只是把层摊到不同卡上，再加上 rank 间传输。 真实模型 PP=4 的 batch=1 只有 13 / 25 / 28 tok/s。想用多卡换延迟只能靠 TP， 而 TP 正是 mid-group 目前过不去的关（MGCKPT/P6.5_TP.md）。

batch=128 那一列（0.97–0.98）落在 §2.3 的噪声带内，不能当"输"—— 另一轮 sweep 在同样位置读到 0.94–0.95。站得住的交叉点是 batch=256： 0.86–0.91，三个 PP 上方向一致，幅度 9–14% 超出带宽。

5. 长上下文（prompt_len 128 → 8192）

数据 p6_pp_longctx.csv，PP=4 / 64 层（真实模型）。

长上下文分裂成方向相反的两个区间，必须分开测，否则一个混合数字会把两边都藏起来：

区间M（GEMM 的行数）预期
解码（KV 很长）= batch（很小）GEMM 成本不变，但注意力随上下文增长 ⇒ 我们的优势被稀释
prefill（prompt 很长）= 整个 prompt（数千）正是 P5 的大 M 冲刷税区间 ⇒ 我们应该输

测量上的分离办法：step_us 的 warmup 与计时跑同一批 prompt 且 prefix caching 开着，所以计时那一跑复用前缀 KV、几乎不付 prefill——**这是刻意的，它让 step_us 即使在 plen=8192 也是纯解码量**。prefill 由 --prefill-probe 用

全新 prompt 的 max_tokens=1 单独测。

plen=128 那一列（156–171 ms）被固定开销主导，五条 arm 基本一样，不要读。

这就是 P5 那条「大 M 结构性冲刷税」第一次在真实引擎的 prefill 上被端到端测到。

6. 部署建议

场景选哪条依据
解码为主、低到中并发（batch ≤ 64）我们的 W4A82.0–2.2× BF16，约 1.1× 我们的 W8A8（§3.2/§4.2）
长上下文解码（8K）我们的 W4A82.05× BF16，五条里劣化最小（+9.6%）（§5.1）
高并发（batch ≥ 256）我们的 W8A8W4A8 在此掉到 0.86–0.91×（§4.3）
prefill 为主 / 长 prompt我们的 W8A8W4A8 只有 W8A8 的 0.64–0.69×（§5.2）
想用多卡降延迟都不行，需要 TPPP 只给容量（§3.4）；TP 见 P6.5_TP.md

最自然的结论是 prefill / decode 分离部署：prefill 侧走 W8A8，decode 侧走 mid-group W4A8。两边的最优解不同，而且差距（1.45× 和 1.1×）都超出噪声带。

不要只因为"W4A8 权重更小"就全链路铺开——它在 prefill 和高并发两个区间都是负收益。
