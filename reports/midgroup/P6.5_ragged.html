1为什么要动契约

原 TP 路线是 GK = 1024/TP（TP=2→GK=512、TP=4→GK=256）。它数值上成立， 但性能上必死：P0_COST.md §5 在固定 K、只变 GK 的对照里 早就量过 —— GK=512 是 1.54–2.57× pc、GK=256 是 2.4–4.1× pc，P0 的判词是 「512 约打平、256 出局」。

P6 测到的行并行停滞（mg/w8 从 0.84 翻到 1.20 / 1.45 / 3.77） 就是 P0 那条代价曲线在 TP 强迫的 GK 上取值，不是新现象。 决定性旁证是 P6 自己的数据：列并行 eff@2 0.92–1.07、eff@4 0.77–1.06 几乎完美 —— 列并行切 N，字节照样按 TP 减少，唯一区别是 GK 没变。

不是「TP 缩放不了」，是「GK 缩小」缩放不了。

所以路线定为：不缩 GK，让算子原生吃任意 K。 底层问题底层解决，不把底层约束推给上层找补。附带效果是这套算子从 「给 QwQ-32B 定做」变成通用算子。

2契约

对外：M、N、K 任意（K=1057、奇数 K、末组只有 1 个元素都要过）。 对内：每个量化组补零到一个 int4 cube fractal（C0 = 32 B = 64 元素）。 

G       = ceil(K / GK)
n_g     = min(GK, K - g*GK)          // 第 g 组真实元素数
n_g_pad = ceil(n_g / 64) * 64        // 补到 fractal
offset  = g * ceil(GK / 64)          // 组起点，对每个 g 都成立

补零是精确的，不是近似的。 补进去的 q_a = 0、 q_w = 0，所以它对 Mmad 贡献 0，对两个 rank-1 修正项 （w_ksum = Σ q_w、a_ksum = −Σ q_a）也贡献 0 —— 因为这两个和是在补齐后的范围上求的，所以没有任何地方需要记录「真实元素数」。 末组的 scale = amax(|x|)/127 也不受影响（补零不抬高绝对值的 max）。

6三条必须一起读的边界

(a) prefill 档我们输给 W8A8，而且不是 ragged 造成的

o/M=512/TP=1 就已经是 1.170 —— 那是 P0/P5 的大 M 结构性税， 跟 TP、跟 ragged 都无关。TP 只让它更明显（M=512：1.170 → 1.386 → 1.449）。 这与 P6 D13 已发布的结论一致（W4A8 是解码方案，prefill 输 0.64–0.69×）， 部署形态仍然是 prefill/decode 分离。

(b) W8A8 在大 M 下超线性缩放，机制未定位

down/M=512 的 w8 是 618.29 → 234.66（2.63×，超过 2）。--cold 的轮换足以冲掉 L2（int8 侧 15 × 70.8 MB = 1.06 GB > 168 MB），所以不是 harness 的 L2 假象。按 P5 D6 的规矩不给它编机制，只记录「大 M 的比值里有 未解释的成分」，不拿它支撑结论。

(c) TP=8 开始碰到新的上限

o/M=128 在 TP=8 是 27.75 µs，比 TP=4 的 26.74 更慢： K_rank=640 时几乎没有 K 活了，每 tile 的固定开销（P5 的 dmaonly 地板）成了主项。 这是下一个杠杆，不是这一轮的问题。

8路上抓到的四个坑

坑为什么值得记
DataCopyPad 的 isPad=false 会把 GM 里紧随其后的真实数据读进补齐区（66 字节请求搬 96 字节） 症状极具误导性：a_scale 全过（同分布多 15 个采样，amax 在 bf16 下常常不变），a_ksum/a_hi/a_lo 全错。「amax 对、和错」直接指向多读了同分布数据，而不是算错了
改 .inc 不触发 kernel 重编 —— ascendc_library 不追踪它 第一次修上一条「没生效」就是这个：编的只有 host，kernel 是旧的，于是拿旧 kernel 出数。已在 build.sh 里堵死
harness 参考实现用 M 而非 Mp 取 a_scale 行距（既有 bug） 只要 M 被补齐就全表 FAIL，看起来像 kernel 坏了。开工时把 ragged 的失败和 M 补齐的失败混在了一起。之所以活到今天：所有既有调用点恰好 M % TILE_M == 0
ragged 让常量组第一次可达，而 asym 量化器在那里是坏的 _tiny_where_zero 把 scale 抬到 tiny，但没管 zero：zero = qmin − round(mn/tiny) ≈ 1e35，在 bf16 里还是有限值，一路传到 kernel 的 wz*a_ksum 才在 fp32 变 inf。一个只护住公式一半的 guard，比没有 guard 更危险

第四条的修复已验证：非退化组（gl=1024/512/128/33）与修改前逐位相同 ⇒ P2 的数字不受影响。它也说明 lab 门禁自己造的输入分布可能恰好绕过真实管线 才会踩的退化情形（这里是 w_zero 是随机生成的而不是从数据算的）， 所以 torch 侧的 seam 测试不是重复劳动。

12fused op 开工调研：原语齐全，MC2 跑不起来

按「不猜先探」的规矩，开工第一步是查原语和定价，不是写 kernel。三个结果：

(1) in-kernel HCCL 原语存在，而且比预想的强

adv_api/hccl/hccl.h 的 class Hccl：AllReduce 加 Commit / Wait 解耦（所以能真重叠）， 而且有 GetWindowsInAddr(rankId) —— 「shared by all ranks in the same comm group」，即内核内直接访问对端显存。

两条设计，第二条才贴合 §10 的测量（贵的是机制不是线）。AllReduce 的 repeat>1 就是分块流水的接口 —— 显式不用。
做法10 KB 上的预期
AHccl::AllReduce + Commit/Wait省掉 op launch，仍走 task/msg 机制
BGetWindowsInAddr + QueueBarrier + 自己在 AIV 里归约完全没有 HCCL task，成本只剩 barrier

(2) host 侧的 context 不用自己造

npu_mm_all_reduce_base(x1, x2, str hcom, ...) 的通信域就是一个 字符串 comm name， pg._get_backend(torch.device("npu")).get_hccl_comm_name(rank) 一行拿到 （vllm-ascend linear_op.py:457 就这么用）。

(3) ⛔ 但 MC2 跑不起来

本想用 CANN 自带的融合算子给项目定价（不写一行 kernel），4 rank 上必然失败： 

aclnnQuantMatmulAllReduceV2 failed, error code is 561000
Nnopbase fails to invoke the HcclAllocComResourceByTiling ... ret = 4

HCCL_BUFFSIZE=200、HCCL_OP_EXPANSION_MODE=AIV 都不解决。

为什么这个负面结果值钱：我们自研的 Hccl::InitV2 会走 同一条 HcclAllocComResource 路径，所以这个阻塞会原样 挡住我们。在一个下午发现它，比写三天 AscendC 之后发现强得多。
