# 910B4 原生 INT4 Cube 验证 + BF16 / INT8 / INT4 GEMM 吞吐对比

日期: 2026-08-10 · 环境: Ascend 910B4 + CANN 8.5.0 + torch_npu 2.7.1
Lab: `vllm/int4_cube_lab/` · 设备: **device 1**（device 0 已挂死，见"环境"一节）

## 结论（一句话）

**910B4 原生支持 INT4 Cube (`mad_s4`)，且其吞吐正好是 INT8 Cube 的 2.0 倍。**
手写 `perchannel_int4_gemm` 在 8192³ 达到 **778 TFLOPS**，是同结构 INT8 kernel
(390 TFLOPS) 的 2.00 倍、官方 `npu_quant_matmul` INT8 (405 TFLOPS) 的 1.92 倍、
官方 BF16 `torch.mm` (219 TFLOPS) 的 3.55 倍。

|------:|----------------:|------------------------:|-----------------:|---------------------:|------------------:|

¹ 512/1024 这两档，官方路径的数字是 **PyTorch 侧 host 分发开销**（每次调用约
25–40 µs 的 Python/ATen 成本）而不是 cube 时间——kernel 本身比分发还快。这两格
不能用来比较硬件，只能说明"从 Python 调小 GEMM 时框架开销占主导"。本文 kernel
走 C++ `aclrtLaunchKernel`，没有这层开销。

**本文 INT8 kernel = 官方 INT8 的 96–98%**（4096³/8192³），说明这套手写流水已经
是生产级水准，因此 INT4 的数字不是"和弱基线比"得来的。

## 2. 关键实验：字节配平（byte-matched）—— 排除"带宽假象"

上表里 INT4 在同样的 (M,N,K) 下只搬一半的字节，所以"快 2 倍"原则上也可能只是
**访存量减半**造成的，而不是 cube 真的更快。为了区分，把 INT4 的 K 翻倍，让两者
**搬运字节数完全相同、Nd2Nz / LoadData / Mmad 指令条数也完全相同**，唯一差别是
每条 Mmad 覆盖的 K 是 2 倍：

| M=N | K(int8) | K(int4) | K 字节 | INT8 µs | INT4 µs | 时间比 | INT8 TFLOPS | INT4 TFLOPS | **算力比** |
|----:|--------:|--------:|-------:|--------:|--------:|-------:|------------:|------------:|-----------:|
| 2048 |   2048 |    4096 |   2048 |   59.58 |   59.83 | 1.004× |      288.34 |      574.25 | **1.99×** |
| 4096 |   4096 |    8192 |   4096 |  353.43 |  349.66 | 0.989× |      388.87 |      786.13 | **2.02×** |
| 8192 |   8192 |   16384 |   8192 | 2767.31 | 2791.76 | 1.009× |      397.32 |      787.68 | **1.98×** |

**同样的字节、同样的指令条数、同样的墙上时间，INT4 完成了 2 倍的乘加。**
这只能由 cube 单元本身的 s4 通路解释，不可能是带宽或指令开销带来的。

## 3. 为什么小 shape 达不到 2×

INT4 的 2× 只在 cube 真正成为瓶颈时才兑现。128×128 输出 tile 的算术强度是
`2·128·128·K / ((128+128)·K/eps)` 字节，与 K 无关；K 越大，单 tile 的 cube 时间
越长，越能盖住 GM→L1 的搬运和 AIC↔AIV 的交接。512³/1024³ 时 tile 数（16/64）
还填不满 20 个 cube 核、且每 tile 的 K 太短，MTE2 与流水启动占主导，所以比值
只有 1.08–1.20×。到 8192³（4096 个 tile、K=8192）比值收敛到 2.00×。

> **⚠️ 这一节的推论被第二轮实测推翻了，见文末"追加"。**
> 当时据此预测"decode（M 小）收益会退化到接近 INT8"——**这个预测是错的**。
> 它只对**方阵**成立：512³ 的总工作量本来就小、tile 数填不满 20 个核。
> 真实的 MLP 形状即使 M=1，N 也有 51200（400 个 n-tile），并行度充足且
> 处于**访存瓶颈**，INT4 照样赢 1.78–1.97×。小方阵吃亏的原因是"总量太小"，
> 不是"M 太小"。

## 4. 实现要点（`kernels/perchannel_lowbit_gemm.inc`）

一份源码同时编译出 INT4 和 INT8 两个 kernel（`QBITS` 宏），**所有缓冲区、DMA
描述符、LoadData 描述符全部按字节表达**——INT4 fractal (16×64 元素) 和 INT8
fractal (16×32 元素) 都是 512 字节，C0 都是 32 字节，所以两个 build 的搬运和
指令数逐条对应，只有 `mm.k` 差 2 倍。这就是第 2 节实验能成立的原因，也让 INT8
build 成为一个天然的受控基线。

INT4 特有的三点：

1. **GM→L1 用 int8 字节视图做 Nd2Nz**（`dValue = K/2` 字节）。int4 沿 K 打包
   （偶数 k 在低 nibble），字节视图保持了 K 方向连续性，32 字节的 C0 块正好就是
   64 个 int4 元素 —— 即 int4 的 C0。不需要特殊搬运。
2. **L1→L0 必须以 `int4b_t` 类型调用 `LoadData`**，让 AscendC 派发到
   `load_cbuf_to_ca_s4` / `load_cbuf_to_cb_s4`（`dav_c220/kernel_operator_mm_impl.h`
   有独立分支）。做法是在调用点对已经按字节偏移好的 tensor 做
   `.ReinterpretCast<int4b_t>()`。用 `int8_t` 类型会走通用 b8 指令，L0 布局不对。
3. **`Mmad` 同样 reinterpret 成 `int4b_t`**，派发到 `mad_s4`；`mm.k` 用**元素数**
   （512），不是字节数。

流水结构（沿用 `NPU-OP/mid_group_gemm_fwd_lab/kernels/perchannel_int8_gemm.cpp`，
已在 910B4 验证）：L1 depth-2 ping-pong + L0 depth-2 ping-pong + 单 L0C 跨整个 K
累加 + 每输出 tile 一次 Fixpipe/一次 CrossCore 交接 + 跨 tile 预取。相对模板的
改动是把"组内固定 4 slice 展开"改成**扁平的 slice 流水**，因此 K 只需要是
`INNER_K` 的倍数（int4: 512，int8: 256），而不是 1024/2048 的倍数——这样
512³ 这类 shape 才能测。

## 5. 正确性

CPU 参考（int32 精确累加 → bf16）逐 shape 比对，`atol=2e-2, rtol=8e-2`：

| shape | int4 | int8 |
|---|---|---|
| 128×128×512 / 128×128×2048（单 tile） | PASS | PASS |
| 512×512×1024/2048（16 tile） | PASS | PASS |
| 1024×1024×2048（64 tile，20 核满载） | PASS | PASS |
| 2048³ | PASS (snr 86.6 dB) | PASS (snr 86.6 dB) |

两个 build 在相同输入下 snr 完全一致，说明 INT4 路径与 INT8 路径算出的是同一个
结果。**race 压测：512×512×1024 与 1024×1024×2048 各连跑 30 次，30/30 PASS**
（int4 与 int8 均是）。

## 6. 环境：device 0 已挂死（重要）

排查开始时，本文 kernel 和**作为参照的、已知正确的**
`mid_group_gemm_fwd_lab/perchannel_int8_gemm` 在 device 0 上都会无限挂起
（launch 后 `aclrtSynchronizeStream` 永不返回，`npu-smi` 显示 health OK、
AICore 0%、无残留进程）。同一个二进制加上 `ASCEND_RT_VISIBLE_DEVICES=1` 立刻
稳定 PASS。

这几乎可以肯定就是 `gemm_precision_lab/CHECKPOINT_2026-08-09.md` 里记录的
"概率性算错 / 失败率在会话中漂移 / 偶尔真的挂起"的成因——**不是
`CrossCoreSetFlag`/`CrossCoreWaitFlag` 写法本身的问题**。该 checkpoint 里
"这套 MIX_AIC_1_2 + CrossCore 写法在高并发下会丢信号"的结论应当撤回：同样的
写法在健康设备上 30/30 稳定。

后续所有测试请显式指定健康设备；device 0 需要 `npu-smi` 复位（需要权限）。

## 8. 已知限制 / 下一步

- M、N 必须是 128 的倍数；K 必须是 512(int4)/256(int8) 的倍数；`K/elemsPerByte`
  必须 < 65536（`Nd2NzParams.srcDValue` 是 uint16）。
- tile 固定 128×128。checkpoint 里试过把 `TILE_N` 改成 256 会 deterministic 全错，
  推测 `mad_s4` 单次调用 N 方向上限是 128；本文没有再碰这条路径。若要进一步提速，
  更有价值的方向是 **TILE_M=256**（L0A 预算够）或 L2 友好的 tile 遍历顺序，而不是
  加宽 N。
- 目前只做了方形 shape。QwQ/Qwen3-32B 的真实形状（K=5120, N=6912, M=16..4096）
  还没扫；decode 档（M 小）预计 INT4 收益会明显退化，值得单独测一轮。
- 尚未包装成 `torch.ops.npu.*`（op-plugin INTEGRATION 路径），当前只是独立
  Kernel Launch 基准。

# 追加（2026-08-10 第二轮）：Qwen3-32B 真实 MLP 形状

维度取 Qwen3-32B（hidden=5120, intermediate=25600, TP=1）：

- `gate_up_proj`：N = 2×25600 = 51200，K = 5120
- `down_proj`：N = 5120，K = 25600
- M = 1, 4, 16, 64, 128, 512, 1024

## 先修的两个 kernel bug（都是 128×128 方 tile 掩盖的）

要测 M=1..64 必须让 TILE_M 小于 128，否则小 M 会被垫到 128。把 TILE_M 参数化
（新增 TILE_M=16 / 64 两组 build）之后暴露了两个 bug，**两个都潜伏在原来的
128×128 版本里**：

1. **`kInnerStrideL1B = INNER_KB * TILE_M` 被同时用于 A 和 B 的 K-slice 步进。**
   A 在 L1 里有 TILE_M 行、B 有 TILE_N 行，两者的 slice 步长只有在
   `TILE_M == TILE_N` 时才相等。已拆成 `kSliceStrideA` / `kSliceStrideB`。
2. **AIV 的 tile 循环缺 write-after-read 同步。** 下一个 tile 的
   `Cast` 会覆写上一个 tile 的 MTE3 仍在读的 `ubBf16Out`；下一个 tile 的
   workspace `DataCopy`(MTE2) 会覆写上一个 tile 的 `Cast`(V) 仍在读的
   `ubInt32`。已补 `MTE3_V` / `V_MTE2` 屏障。
   **这个 bug 在 TILE_M=128 下是潜伏的**——两个 chunk 加上较慢的 cube 让窗口
   一直关着；TILE_M=16 时 cube 套圈 vector，就变成稳定复现的损坏
   （blockDim>1 且 tile 数 > blockDim 时必现，SNR 每次运行都不同）。
   同一个隐患也存在于 `mid_group_gemm_fwd_lab/perchannel_int8_gemm.cpp` 模板里。

**顺带修了检查本身**：原来只有 `atol=2e-2 / rtol=8e-2`，而这些形状的输出量级
只有 ~1e-3，于是**完全错误的输出也能 PASS**。第一版 TILE_M=16 就是这样假 PASS
的（SNR 只有 0.5 dB）。现在 pass 条件加了 SNR ≥ 40 dB 的下限（正确的 kernel
稳定在 80–117 dB）。

## 再修一个测量方法问题：L2 把结果吹高了

910B4 的 L2 是 **168 MiB**。benchmark 循环里反复用同一个权重张量，权重就一直
待在 L2 里——真实推理不会这样，64 层各自的权重都要从 HBM 流过来。
实测 `down_proj` M=1：INT4 热 35.8 µs → 冷 63.8 µs（慢 78%），INT8 热 101.3 µs
→ 冷 115.0 µs（慢 14%）。INT4 权重更小、更容易整个装进 L2，所以**热测量会系统
性地夸大 INT4 的优势**（热态下 INT4/INT8 一度报出 2.8–3.0×）。

因此本节所有数字都是 **cold**：轮换足够多份权重副本（总量 >1 GiB）把 L2 冲掉，
自定义 kernel 和官方路径都一样处理。

## 读法

1. **INT4 在 M=1..1024 全程领先，倍数 1.78–2.74×（对同结构 INT8）**，而不是
   方阵测试里那样"只有大 M 才有 2×"。原因变了：方阵 8192³ 是 cube 瓶颈；这些
   MLP 形状在整个 M 区间都是**访存瓶颈**（小 M 是 HBM 权重流，大 M 是 L2 带宽），
   而 INT4 在每一层存储上都恰好减半。cube 的 2× 和访存的 2× 指向同一个方向。
   `down_proj` 大 M 出现 2.5–2.7×（超过 2×）是因为 INT4 的工作集更小、L2 命中
   更好——这是真实收益，但属于访存层级效应，不是 cube 又变快了。
2. **官方 W4A16（`npu_weight_quant_batchmatmul`）在小 M 比 BF16 `torch.mm` 还慢**
   （729 vs 439 µs）。它把 int4 反量化成 bf16 再走 bf16 cube，权重省了但算力没省，
   反量化开销还盖过了收益。**这就是 vLLM 今天的 W4 路径**——对 decode 是负优化。
   本文的 int4-cube kernel 比它快 **4.2–10.9×**。这是本轮最有行动价值的一条。
3. **本文 INT8 kernel 在这些形状的大 M 端落后官方 1.33–1.42×**（方阵 8192³ 是
   打平的）。所以"×INT8官方"那一列在 M=512/1024 **低估**了硬件潜力——把 INT4
   kernel 按官方 INT8 的水平调优后，还有约 1.4× 的空间。

## 对 vLLM W4A8 的推论（分析，非实测）

本文实测的是 **W4A4**（两个操作数都是 int4）。cube 要求两个操作数等宽，所以
W4A8 只能：

- **把权重升到 int8**：cube 的 2× 全部丢掉，只剩权重访存减半。在 decode
  （访存瓶颈）仍有收益，prefill 基本无收益。
- **MSD 分解**：把 int8 激活拆成 int4 分量。两项分解（`A8 = 16·A_hi + A_lo`）
  = 2 次 int4 GEMM，在 2× 速率下**算力与单次 int8 GEMM 打平**，而权重访存减半
  → decode 净赚、prefill 不亏。若某种实现需要 3 次分解，则算力变成 int8 的
  1.5 倍时间，prefill 反而亏。**分解项数是这条路线成败的关键**，值得先确认。
