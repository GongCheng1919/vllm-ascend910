# W4A8 per-channel GEMM：原生实现与 vs W8A8 吞吐对比

日期: 2026-08-10 · 环境: Ascend 910B4 + CANN 8.5.0 + torch_npu 2.7.1
Lab: `vllm/int4_cube_lab/` · 设备: **device 1**（device 0 已挂死，见 REPORT.md §6）

## 结论（一句话）

**W4A8 不但达到了 W8A8，还全面超过它**：Qwen3-32B 的 MLP 形状上，M=1..16（decode）
快 **1.65–1.88×**，M=1024（prefill）快 **1.57–1.62×**；且在 M ≤ 16 时只比纯 W4A4
慢 3–8%。这是在**同一套流水、同一份 host harness、同样 tile 几何**下的对照测试。

## 1. 为什么 W4A8 必须做 MSD 分解

`kernel_operator_mm_impl.h:317` 的 `MmadCal` 只接受两种整型组合：

```
Tuple<int32_t, int8_t,   int8_t>     -> mad
Tuple<int32_t, int4b_t,  int4b_t>    -> mad_s4
```

**cube 没有 s8×s4 混合位宽指令。** 所以"A 8bit、W 4bit"只有两条路：

- 把 W 升到 int8 → 权重就不再是 4bit，访存收益归零，纯亏；
- 把 A 拆成两个 int4 平面走 `mad_s4`（MSD 分解）。

本文走第二条。REPORT.md 末尾对 W4A8 的分析预测"两项分解 = 算力与 W8A8 打平、权重
访存减半"，本文把它实现出来并实测——**结论比预测更好**（见 §4）。

### 精确分解（覆盖全 int8 范围，不需要 clamp）

朴素的对称二项分解 `a = 16h + l`（h、l ∈ [-8,7]）值域只有 [-136,119]，
表示不了 a=120..127，必须把量化器范围砍掉 0.09 bit。本文用带偏置的形式，**对全部
256 个 int8 值都精确**：

```
a = 16*h + l + 8,   h = a >> 4        ∈ [-8,7]   （int8 的高 nibble，即有符号 int4）
                    l = (a & 15) ^ 8  ∈ [-8,7]   （低 nibble XOR 8，即 v-8 的 int4 编码）
```

代回 GEMM：

```
C[m,n] = Σ_k a·w = 16·Σ_k h·w  +  Σ_k l·w  +  8·Σ_k W[n,k]
                                              └────┬────┘
                                        与 m 无关的 per-channel 常数
```

末项由 host 预先算好的 `w_ksum[N]`（int32）提供——这是**权重侧的一次性预处理**，
和 w_scale 同级别，推理时零成本。

两个 A 平面各 K/2 字节，合计 K 字节，**与 int8 的 A 完全一样大**；W 是 K/2 字节，
**是 int8 的一半**。两条 `mad_s4`（2× 速率）耗时 = 一条 `mad`。所以理论上：
cube 时间打平，访存全面减少。

### 实现：stacked-A（一条 Mmad、一个 L0C、一次 Fixpipe）

没有用"两条 Mmad 打进两个累加器"，而是把 h 平面和 l 平面**沿 M 方向叠**成一个
`2*TILE_M` 的 cube tile，共享同一个 B：

```
L1 A tile (NZ, dstNzC0Stride = 2*TILE_M)
   rows [0, TILE_M)        <- a_hi   （Nd2Nz 第一次调用）
   rows [TILE_M, 2*TILE_M) <- a_lo   （第二次调用，dst 偏移 TILE_M*32 字节）
```

于是 AIC 侧的每一个描述符都是 W4A4 kernel 把 `TILE_M` 换成 `TILE_MC = 2*TILE_M`
的结果，指令结构一模一样。AIV 拿到 workspace 后做

```
c = 16*C[0:TILE_M] + C[TILE_M:2*TILE_M]        （int32 内精确相加）
y = (c + 8*w_ksum[n]) * w_scale[n] * a_scale[m]  （fp32 → bf16）
```

`16*C_hi` 用 int32 `Muls`+`Add` 完成再 Cast，避免 fp32 在 2^24 以上丢低位。

### 片上预算（这是 TILE_M 上限的来源）

A 侧 cube 行数翻倍，L0A 就要翻倍。910B4：L1 512 KB、L0A/L0B 各 64 KB、L0C 128 KB。

| TILE_M | cube tile | INNER_KB | L0A(×2) | L0C | L1 |
|---:|---:|---:|---:|---:|---:|
| 16 | 32×128 | 256 | 16 KB | 16 KB | 320 KB |
| 32 | 64×128 | 256 | 32 KB | 32 KB | 384 KB |
| 64 | 128×128 | 256 | **64 KB** | 64 KB | **512 KB** |
| 128 | 256×128 | 128 | **64 KB** | **128 KB** | 384 KB |

TILE_M=128 必须把 L0 slice 深度砍半（INNER_KB 256→128 字节）才放得下 depth-2
ping-pong；对应 K 的对齐要求从 512 变成 256 元素。TILE_M=128 是硬上限——再大
L0C 就爆了。（顺带确认了 910B4 的 L0C 确实是 128 KB：256×128 的 int32 tile 跑通了。）

## 5. 读法

1. **"W4A8 能不能达到 W8A8"——能，而且是大幅超过。** 小 M 尤其明显：M ≤ 16 时
   1.65–1.88×。原因很直接：decode 是**权重流带宽瓶颈**，cube 基本闲着，W4A8 把
   权重字节砍半就等于把时间砍半；MSD 多出来的那条 `mad_s4` 落在闲置的 cube 上，
   一分钱不花。
2. **小 M 时 W4A8 ≈ W4A4（差 3–8%）。** 这说明 decode 档"A 用 8bit 还是 4bit"
   几乎不影响速度——**激活可以保留 8bit 精度而几乎不付性能代价**。对精度敏感的
   部署，这是比 W4A4 更实用的点。
3. **W4A4 的优势只在 M 变大后显现**（M ≥ 128 领先 W4A8 1.2–1.7×），因为那时
   cube 成了瓶颈，W4A4 的 MAC 数只有 W4A8 的一半。M=128 是 gate_up 的交叉点。
4. **W4A8 的 2× 上限在哪。** 相对 W8A8 的理论上限是 2×（权重减半、A 不变、cube
   打平）；实测 M ≤ 16 拿到 1.86×，已经很接近。剩下的差距是 A 和输出的字节，
   以及 W4A8 那一份 int8 A 在 cube tile 里占了 2×TILE_M 行带来的 L1 压力。
5. 对比 REPORT.md 里的官方基线：官方 `npu_weight_quant_batchmatmul`（W4A16，即
   vLLM 今天的 W4 路径）在 gate_up M=1 是 729 µs。本文 W4A8 是 123.7 µs，
   **快 5.9×**，而且激活是真 8bit 量化而不是 bf16。

## 7. 已知限制 / 下一步

- **A 的 MSD 拆分由 host 完成。** 在真实推理里这一步属于 per-token 量化 kernel
  的职责：它本来就要写出 int8 激活，改成写两个 int4 平面（`a>>4` 和 `(a^8)&15`）
  是同一趟 elementwise，字节总量不变。本 lab 没有实现那个 kernel，所以 §3 的
  数字**不含**拆分成本；对 M=1、K=5120 来说那是 5 KB 的 elementwise，相对 123 µs
  可以忽略，但要在端到端里验证。
- `w_ksum[N]` 是权重侧一次性预处理，已在 host 算好；上线时应和量化权重一起存盘。
- N 必须是 128 的倍数；K 的对齐见 README；`K/2 < 65536`（`Nd2NzParams.srcDValue`
  是 uint16），即 K < 131072。
- TILE_M 上限 128（L0C 128 KB 卡死）。TILE_N 仍固定 128。
- 只测了 MLP 两个投影，attention 的 QKV/O 和 TP 分片形状没测。
- 尚未包装成 `torch.ops.npu.*`，当前是独立 Kernel Launch 基准。
- M=512/1024 端，本文的 W8A8 baseline 本身比官方 `npu_quant_matmul` 慢约 1.4×
  （REPORT.md 读法 3），所以那一段的"W4A8/W8A8"是同结构对比，不等于对官方最优
  实现的加速比。

## 本轮结论

1. **W4A8-pc 的领先在 attention 投影上也成立**：M=1/16 时 qkv/o 快 **1.28–1.44×**，
   gate_up/down 快 **1.69–1.88×**。qkv/o 的倍数偏小是因为它们的 N 小（7168/5120）：
   decode 档里 A 流、输出写回、启动这些与 N 无关的固定开销占比更高，权重减半的收益
   被摊薄。
2. **mid-group 在 910B4 上没有任何赢面——所有 gk 都慢于 per-channel**：
   - gk=1024：M ≤ 64 慢 **5–13%**（1.05–1.13×）；M=512/1024 慢 **37–47%**，此时
     **连 W8A8 都打不过**（0.76–0.85×）；
   - gk=512：M ≤ 64 慢 1.4–2.0×，M=1024 慢 2.2–2.4×；
   - gk=256：M ≤ 64 慢 2.3–3.9×，M=1024 慢 3.7–4.1×。
3. **代价基本随组数线性增长**：GK 每减半（1024→512→256，组数翻倍），时间约翻倍
   （gate_up M=1：149.7 → 267.2 → 520.8 µs）——符合"每个输出 tile 的 scale 处理
   次数 ∝ 组数"的解释，而 per-channel 每 tile 只有一次。
4. **结论**：910B4 上 W4A8 就用 per-channel；mid-group 的灵活性（每组独立 scale，
   对组内 outlier 更稳）要付实打实的性能税，GK 越大越接近 per-channel，但追不上。

W8A8 都打不过"——那条针对的是 `M=512/1024`（tile=128）。**在 M=64（tile=64）
四个投影 mg 全部超过 W8A8（1.16–1.53×）**。本文 8.2 的"慢 5–13%"是针对
per-channel 的，per-channel 在 decode 档本来就大幅领先 W8A8，两者不矛盾：
**mg ≤ pc < W8A8 的性能序在 M≤64 成立，划线的"超过 W8A8"达标。**

## 4.2 瓶颈定位：AIC 的 GM→L1 节奏（MTE2 82%），不是带宽、不是 AIV、不是 scalar

`msprof`（PipeUtilization，qkv M=512，见 `po_mg_pipe/`）：

| 指标 | mg dmaonly（纯搬运） | perchannel w4a8 |
|---|--:|--:|
| AIC MTE2 忙率 | 0.82 | 0.75 |
| AIC scalar | 0.82 | 0.84 |
| AIC Fixpipe | ~0 | 0.11 |
| AIV vec / mte2 | ≈0 | 0.15 / 0.12 |

- **MTE2 只有 82%**：折 0.93 TB/s < HBM ~1.1–1.25 TB/s 有效峰值 → **没撞带宽墙**。
- **Fixpipe 只有 0.11**（折 ~2.9 TB/s）→ 写路径不慢；nofix 省 49µs 的真因是松掉
  L0C 端口/credit 同步链，不是 Fixpipe 吞吐。
- **scalar 与 MTE2 同步推进（都 0.82）**，但静态数指令量级不足 30% 预算。
- 结论：时间花在 **L1 depth-2 双缓冲 + 组边界发射的节奏反压**上，是结构性节奏税，
  不是某条指令串行，也不是带宽。P5 四轮调度改动全部 ≤5% 与此一致。

## 4.3 已逐一证伪的方向（不必再重复投入）

| 方向 | 结论 |
|---|---|
| 加深 workspace slot（2→10，id 轮询全异步）| P5 §3'.1 已判死：noaiv 证明 AIV 不是瓶颈，无等待可掩盖；L0C depth=1 是硬件限不死软件加深 |
| cube 做 diag(scale)·INT32·diag(scale) | 指令集无此形态（L0C 是 int32、cube 只收 int4/int8）；AIC/AIV 双核并行无"切换核心"机制；D10 的 DEQF16 是唯一出口且实测负收益 |
| bf16/half workspace 中转 | D10 实测**减半字节反而慢 3.9–6.2%**（fp16 尾巴 + AIV 多 3 条向量指令）|
| 放大 L1 slab（fewer per-group loads）| **静态证伪**：`2*(256+128)*GROUP_KB ≤ 512KB` ⇒ GROUP_KB=512 ⇒ 每组一个 slab，发射税结构性不可摊薄 |
| 大 GK（2048）| GK 是权重格式属性，非按 M 可变；改它要重开 P2 精度评估 |
| TILE_M=64 改派 | P5 §3''.4：因 1/TILE_M 权重流量翻倍，反而慢 1.17–1.38× |

净判断：**M=64 的 decode 档已达标，默认 int32 中转即可；剩余大 M 税是 MSD 双平面
int32 workspace 的结构性代价**——要省只能回 `MID_GROUP_ROADMAP` 层面讨论大 M 是否
另走 kernel 家族。

## 4.4 ⚠️ 数值回归告警（影响任何同步/部署，暂缓 BAND 默认化）

做 BAND_N 默认化（P5 第 7 步）前置检查时发现：**当前工作区 midgroup（含 ragged-K
改造，`mg_kgeom.h`）在 N 较大/每 block 多 tile 时有确定性数值错位**：

- `qkv M=512 N=7168 K=5120 --check`: **967405 mismatches, snr 7.6dB**（`mismatch=0` 的
  P5 记录是旧提交版数据）。
- `perchannel_w4a8_gemm` 同 shape **PASS**（snr 94.9）→ 问题特定于 midgroup。
- `N=2560` 也 FAIL；`M=128/N=2560`、`M=128/N=128` **PASS** → 随每 block tile 数变化，
  **与 BAND_N 无关**（BAND=0/1 结果一致，profiling/划线测试均为 `--profile` 未校验数值，
  故此前未暴露）。

**因此 BAND_N 默认化、同步 npu_ops、e2e 均被该回归阻塞**，lest 把错 kernel 部署进
vLLM 路径。修复属独立排查（workspace 双 slot 跨 tile 复用 / ragged 打包或寻址），
不在本轮范围内。本会话对 band 的改动已 revert，lab 与 npu_ops 保持一致为 `BAND_N=0`。
