## ★★ 一句话给接手的人（PP，本期交付）

**PP 是今天就能部署的那条并行，我们的优势在它下面一点没掉。** 真实 64 层

## ★ 一句话给接手的人（TP，已转 `P6.5_TP.md`）

**对齐从来不是问题，性能才是。** `GK = 1024/TP` 这条零 kernel 改动的路线在数值上
完全成立（逐位过），但 mid-group 在**行并行投影（o_proj / down_proj）上几乎不随 TP
缩放**——TP=2 的每卡耗时和 TP=1 一样，TP=4 也一样。后果是从 TP=2 起
**mid-group W4A8 就输给普通 W8A8**（1.13–2.06×，TP=4 最坏 3.77×），
它存在的理由在 TP 下消失了。

而且**这不是分组冲刷造成的**（`nofix` 地板同样不缩放），机制尚未定位——
按 D2 的规矩，**在拿到 dmaonly 梯子之前不要猜、不要改 kernel**。

**建议的下一步（未执行，等决策）**：

1. 先跑 dmaonly 梯子定位那个与 K 无关的固定开销。它**同时压着 mid-group 和 pc
   两条路**，比继续啃冲刷值钱。
2. 若要上 TP，行并行改走 **per-channel W4A8**（会缩放、精度代价随 TP 变小），
   mid-group 只留在列并行的 qkv / gate_up 上。`npu_ops/` 目前**没有** per-channel
   W4A8 kernel，只有 lab 里有。
3. **不要**再投入"支持 ragged group"——那是伪问题（D1）。

拒掉（TILE_M=128 的 build `kAlign=256`，所以 M=128/512 那几行有数）。
**这是 harness/tiling 约束，不是算法约束。**

## 3. 决策与坑

### D1 · 「K 不对齐」是个伪问题，真问题在下一层

上一轮担心 TP 切 K 之后凑不齐 g1024。实际上：kernel 的 **L1 slab 层级本来就
ragged-tolerant**（`lastGSlices`，K=5120 就是 5 组分 3 slab），硬对齐的是**量化组
层级**——`TORCH_CHECK(K % 1024 == 0)`、`numSlices = Kb/INNER_KB` 的截断除法、
以及 AIC↔AIV 写死成常数 `SLICES_PER_QGROUP` 的 flush 节奏。

但这一层也不用改，因为 `2^10 | 5120` 且 `2^10 | 27648`，`GK = 1024/TP` 恒整除。
**花在"怎么支持 ragged group"上的时间会是白工。** 真正的坑在性能，不在格式。

### D2 · 行并行的停滞**不是**分组冲刷造成的 —— 我的假设被自己的对照推翻

原假设（上一轮跟用户讲的）：冲刷次数在 TP 下不变
（`(K/TP)/(1024/TP) = K/1024`）而算力活儿按 TP 缩小，所以冲刷占比会随 TP 放大。
**占比确实放大了**（o/M=512 的 tax 从 30.9% → 42.6%），**但那不是停滞的原因**。

`nofix`（把 Fixpipe 整个删掉）同样不缩放：

| proj | M | nofix@TP1 | nofix@TP2 | nofix@TP4 | eff@2 | eff@4 |
|---|--:|--:|--:|--:|--:|--:|
| o | 16 | 24.17 | 24.30 | 24.04 | 0.497 | 0.251 |
| o | 512 | 74.50 | 60.81 | 61.23 | 0.613 | 0.304 |
| down | 512 | 364.19 | 270.05 | 269.51 | 0.674 | 0.338 |
| down | 1024 | 698.49 | 524.16 | 523.34 | 0.666 | 0.334 |

删掉冲刷之后 eff 仍然只有 0.50–0.67 / 0.25–0.39。**存在第二个、与 K 无关的成本，
而且它才是主项。** 量级参考：o/M=16/K=1280 的 nofix 用 24 µs 搬了约 4 MB
（0.17 TB/s），比这个 kernel 在别处的 1–3 TB/s 低一个数量级，所以像是**每 tile 的
固定开销**而不是带宽。但这只是量纲推断，**没有证据前不要当结论**——见待办第 1 项。

教训与 P5 D6 同型：「机制解释属实」≠「它是主因」。这次是「占比确实涨了」
≠「涨的那部分就是停滞的原因」。

### D3 · L2 分带在解码档是**恒等变换**，不是"白赚"

`BAND_N_CFG` 只在 `numMTiles > 1` 时才改变遍历顺序。`numMTiles == 1` 时
`fullBandTiles == superN`，于是 `mTile = within/superN = 0`、`nTile = tileId`，
**逐字节退化成原来的平铺**。而 host 的 `TileMFor`（M≤16→16、M≤64→64、否则 128）
保证了：

| TILE_M | 触发条件 | Mp | M-tile 数 |
|---|---|--:|--:|
| 16 | M≤16 | 16 | **1** |
| 64 | M≤64 | 64 | **1** |
| 128 | M>64 | ceil(M/128)·128 | **M≥256 才 >1** |

所以**分带只可能在 TILE_M=128 且 M≥256 时起作用，即只有 prefill**。P4 调的整个
解码区间（batch 1–128）结构上够不着。P5 交接清单里"白赚 2~4.6%"的说法要按档位
限定：**prefill 白赚、decode 归零**。

设默认本身是安全的（在两个解码档是恒等），但别指望它改善 P4 的解码口径。

### D4 · 这套 harness 的噪声地板是 ±2.6%，比 P5 若干结论的幅度还大

`results/p6_band_noisefloor.csv` 的 12 行里，qkv/o 那些行的两个 binary 是
**可证明同路径**的（N·Kb 在 32 MB 上限以下 **且** numMTiles=1，双重 no-op），
却读出 −2.64% 和 −1.82%：

| proj | tileM | M | base µs | band µs | Δ |
|---|--:|--:|--:|--:|--:|
| qkv | 64 | 64 | 41.28 | 40.19 | **−2.64%** |
| o | 64 | 64 | 32.97 | 32.37 | −1.82% |
| gate_up | 128 | 128 | 299.81 | 299.61 | −0.07% |

**这就是 median-of-3 协议的噪声地板。** 直接后果：P5 D9 报的 gate_up M=512
**−2.8%** 落在噪声带内，不能当实数；M=1024 的 −4.6% 才站得住。P6 起 band 类
测量一律 median-of-5，并且**每张表都要带一个可证明同路径的对照行**。

### D5 · `--check` 的形状必须落在被测分支上，否则测了个寂寞

第一版 `check_p6.sh` 给 band 用 N=1280 图省 CPU 参考时间。但 banding 的开关是
`N·Kb > 32 MB`——N=1280/K=27648 只有 17.7 MB，`superN` 退化，**banded 分支根本
没执行**，6 个 PASS 一个都不算数。改成 gate_up（141.6 MB）和 down（70.8 MB）
之后才是真的在测，并额外保留 qkv/o 两个 no-op 对照确认映射没写反。

凡是"只在某条件下才启用"的优化，门禁形状要**同时覆盖启用和不启用两侧**。

### D6 · 决定性的对照是"跟别人比"，不是"跟自己比"

`sweep_p6_tp.sh` 把 mid-group 跟它自己比，只能得出"TP 下变贵了"，**推不出任何
决策**。加了 `sweep_p6_tp_alt.sh`（mg / pc / w8 三方）之后结论才立起来——见下节。

### D7 · PP 下的两点斜率法必须固定**每卡层数**，否则读出物理上不可能的数

第一版 `sweep_p6_pp.sh` 把**总层数**固定在 4/16，于是 PP=4 只有 1 层和 4 层/卡。
算出来 **BF16 的每层斜率 PP=1 是 1047.9 µs、PP=4 是 310.6 µs** ——「开 PP 让一层
便宜了 3.4 倍」。**这在结构上不可能**：PP 按层切，层内一点没切。

失效的是斜率法的前提：`step(L) = 截距 + L × 每层`，且**截距与 L 无关**。PP 下截距
随"层怎么分布到 rank"而动（1 层/卡时通信和气泡把它撑爆），两点法就废了。
改成固定每卡层数（`sweep_p6_pp_isorank.sh`）之后，**BF16 斜率立刻变成
1071/1084/1117 跨 PP 基本不动**——这个"应该是常数的量真的是常数"就是该方法
恢复有效的证据。

同一个坑还有第二个出口：那一版的 PP=4 让三条 arm 全部收敛（43/41/44 tok/s），
差点被读成"我们的 kernel 在 PP 下失效了"。真正的原因是 **4 层/卡时 GEMM 已经
不是大头**。凡是并行度实验，**先问"每卡还剩多少活"**，再看比值。

### D8 · worker 转没转，只能**问**，日志里没有那行不是证据

`[midgroup] N linears converted` 只在 `converted % 64 == 0` 时打，短 `--layers`
跑永远到不了 64；而父进程的计数器在 `tp*pp>1` 时天然是 0（模型在 worker 里）。
两个一叠加，**"没看到转换日志"和"真的没转"长得一模一样**——2026-08-15 的 PP=4
就是这么被当成 W4A8 测的（实际全程 BF16）。

现在 `bench_engine_decode.py` 用 `collective_rpc(_rank_conversion_stats)`
**逐 rank 查**，任何一个 rank 转了 0 就 `return 2` 拒绝出数：

```
[bench] rank 0: pid=... arm=w4a8 converted=64 skipped=0
[bench] rank 3: pid=... arm=w4a8 converted=64 skipped=0
```

64 = 16 层/卡 × 4 个投影，能跟配置对上账才算数。**测量脚本的正确性判据必须是
主动查询的返回值，不能是日志的缺席。**

### D9 · `tp*pp>1` 起不来是 fork + OpenMP，不是我们的 patch

worker 一启动就 `pool INTERNAL ASSERT FAILED ... Invalid thread pool!` 然后
`WorkerProc initialization failed`。原因：`VLLM_WORKER_MULTIPROC_METHOD` 默认
`fork`，而 `MultiprocExecutor` **只在环境里没有 `OMP_NUM_THREADS` 时**才在子进程里
调 `torch.set_num_threads(1)`；父进程已经初始化过 OpenMP，fork 之后再调就炸。

修法是在 `bench_engine_decode.py` 顶部 `setdefault("OMP_NUM_THREADS", "1")`
把那条分支拿掉，**不依赖调用方记得在命令行加**。查这类"多进程一开就挂"先看
栈顶是不是 fork 之后的线程池/句柄操作，别先怀疑自己的 patch。

### D10 · PP 给的是**容量**，不是延迟——别拿它当加速比读

一个 token 仍要串行穿过全部 64 层，PP 只是把层摊到不同卡上，所以**单请求的每步
延迟只会变差**（真实 64 层 PP=4 的 batch=1：BF16 13、我们 W8A8 25、我们 W4A8
28 tok/s）。`p6_pp_engine.csv`（固定总层数）读出的"PP 越大越慢"是**对的**，
不是 bug。

直接后果有两条：**(a)** PP 表里跨 PP 比 tok/s 是错的（那是不同大小的模型），
只能同 PP 内横比 arm；**(b)** 要用多卡换延迟就必须上 TP，而 TP 正是
mid-group 目前过不去的那关（§1.4）——**这两件事合起来才是 `P6.5_TP.md`
存在的理由。**
