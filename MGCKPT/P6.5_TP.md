## ★ 一句话给接手的人

**TP 是唯一能用多卡换延迟的并行**（PP 只给容量，`P6_TP.md` D10），
而 mid-group W4A8 恰恰过不去这一关：**行并行投影不随 TP 缩放**
（eff@2≈0.51、eff@4≈0.26），从 TP=2 起就**输给普通 W8A8**（1.13–2.06×，
TP=4 最坏 3.77×）。数值对齐早就证明不是问题，**性能才是**。

机制**仍未定位**——已知"不是分组冲刷"（`nofix` 同样停滞），
按 `P6_TP.md` D2 的规矩：**拿到 dmaonly 梯子之前不要猜、不要改 kernel。**

**开工第一件事是 D0 的门禁 bug**，因为它会让 TP 下的 W8A8 基线是假的，
而 W8A8 正是这一期所有比较的分母。

## 1. 待办（按依赖排序）

1. **修 D0 的门禁 bug**（最先，几行）。没有它，TP 下的 W8A8 基线是
   66% W8A8 + 34% BF16 的混合体，而这一期所有结论都要拿 W8A8 当分母。
   修完顺手把 `bench_engine_decode.py` 的对齐检查从"只拦 w4a8"扩到**所有 arm**。
2. **dmaonly 梯子跑在 TP 形状上**（最高优先的技术项）。当前只知道"不是冲刷"，
   不知道是什么。需要 `midgroup_w4a8_gemm_m{16,64,128}_g{512,256}_asym_dmaonly`
   六个 build，在 o/down 的 TP=1/2/4 形状上跑完整梯子
   （pc / full / noaiv / nofix / dmaonly）。**拿到证据之前不要改 kernel。**
   量级参考：o/M=16/K=1280 的 nofix 用 24 µs 搬了约 4 MB（0.17 TB/s），
   比这个 kernel 在别处的 1–3 TB/s 低一个数量级，**像**是每 tile 的固定开销
   而不是带宽——**这是量纲推断，不是结论。**
3. **per-channel W4A8 补齐 K 对齐**：lab 的 `perchannel_w4a8_gemm*` 在
   K=1280/6912 上被 harness 直接拒（`kAlign = INNER_KB*2 = 512`），
   所以 `p6_tp_alternatives.csv` 里 TP=4 那列缺 pc 数据。
   **这是 harness/tiling 约束，不是算法约束**，要放开——而 pc 恰好是
   第 2 项若无解时的备选路线，缺这列就等于缺退路的证据。
4. **npu_ops 侧**（等第 2 项结论）：`kGroup` 从 `constexpr 1024` 改成由
   `K / a_scale.size(0)` 推导（scale 张量本来就隐含组大小），switch 从 3 个
   kernel 扩到 3×3。**没有第 2 项的结论就动，可能白做。**
5. 两份 `.so` 重编（P4 D5）。

**明确不要做的**：再投入"支持 ragged group"。那是伪问题——`2^10 | 5120` 且
`2^10 | 27648`，`GK = 1024/TP` 恒整除，花在这上面的时间是白工（`P6_TP.md` D1）。

## 2. 决策与坑

### D0 · `_supported()` 拿 mid-group 的组约束去卡 W8A8，会安静地产出假数据

`npu_ops/python/vllm_engine_patch.py:173`：

```python
def _supported(w) -> bool:
    n, k = w.shape
    return (k % GROUP == 0) and (n % TILE_N == 0)      # GROUP = 1024
```

这个 `k % 1024` 是 **mid-group W4A8 kernel 的**约束，但 `_supported()` 对
**两条 arm 都生效**。而 `W8A8Linear` 走的是 `npu_dynamic_quant` +
`npu_quant_matmul`，**per-channel，根本不需要 K 对齐**。

后果（QwQ-32B，任何 TP>1 都命中——5120 和 27648 除以任何 TP 都不是 1024 的倍数）：

| proj | K | TP=2 的 K_rank | %1024 | TP=4 的 K_rank | %1024 |
|---|--:|--:|--:|--:|--:|
| o_proj | 5120 | 2560 | 512 ❌ | 1280 | 256 ❌ |
| down_proj | 27648 | 13824 | 512 ❌ | 6912 | 768 ❌ |

于是 `--arm w8a8 --tp 2` 会**正常跑完并报出一个数**，而那个数其实是
**66% W8A8 + 34% BF16**——o_proj 和 down_proj 被静默留在 BF16 了。
`bench_engine_decode.py` 的对齐门禁只拦 `patch_arm == "w4a8"`，**拦不住这条**。

修法：按 arm 拆门禁（W8A8 只留 `n % TILE_N`），并把 bench 的检查扩到所有 arm。
**这是本期第一件事**——W8A8 是所有 TP 比较的分母。

> 教训与 `P6_TP.md` D8 同型：**一个"安静地少做了一部分工作"的路径，
> 跟"正常工作"在输出上长得一模一样。** 凡是"不支持就跳过"的分派，
> 跳过时必须要么报错要么计数可查，不能只是 `return stock(...)`。

### D1 · 继承自 P6 的三条，不要重新推导

1. **对齐是伪问题**（`P6_TP.md` D1）：kernel 的 L1 slab 层级本来就 ragged-tolerant，
   硬对齐的是量化组层级，而 `GK = 1024/TP` 对 QwQ-32B 恒整除。
   16/16 `--check --stress 10` mismatches=0。**格式没问题，别再查了。**
2. **停滞不是冲刷造成的**（`P6_TP.md` D2）：`nofix`（把 Fixpipe 整个删掉）
   同样不缩放（eff@2 0.50–0.67）。存在第二个、与 K 无关的成本，**它才是主项**。
3. **决定性的对照是跟别人比**（`P6_TP.md` D6）：mid-group 跟自己比只能得出
   "TP 下变贵了"，推不出决策。三方对照（mg / pc / w8）才立得住结论。

### D2 · TP 会让 mid-group 的权重**不能跨 TP 复用**——这是部署成本，不只是性能问题

`GK = 1024/TP` 意味着 **TP=2 和 TP=4 要的是两份不同量化的权重**
（组大小分别是 512 和 256）。也就是说改 TP 就得重新量化一次模型，
checkpoint 跟并行度绑死。

per-channel 路线没有这个问题，而且它的**精度代价随 TP 变小**
（TP=2 时一个 scale 管 K/2=2560 个元素，TP=4 时只管 1280）——
**TP 越大 pc 越划算，跟 mid-group 的走向正好相反**（`P6_TP.md` §1.4 结论 2）。
选路线时把这条算进去，别只看 µs。
