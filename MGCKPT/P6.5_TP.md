## ★ 一句话给接手的人

**问题的根不在 TP，在算子契约里那一行 `K % 1024 == 0`。**

原路线是 `GK = 1024/TP`（TP=2→GK=512、TP=4→GK=256），它数值上成立但**性能上必死**——
因为 `P0_COST.md` §5 早就在**固定 K、只变 GK** 的对照里量过：GK=512 是 1.54–2.57× pc、
GK=256 是 2.4–4.1× pc，P0 的判词是"512 约打平、256 出局"。P6 的 TP 表
（mg/w8 从 0.84 翻到 1.20/1.45/3.77）**就是 P0 那条代价曲线在 TP 强迫的 GK 上取值**，
不是新现象。真正 TP-不变的量是 `numQGroups = K/GK`，而 `GK = 1024/TP` 恰好把它钉死。

**用户 2026-08-17 决定的路线：不缩 GK，也不做上层不均匀分片，而是让算子原生支持任意 K。**
理由是架构性的：底层问题底层解决，不要把底层约束推给上层找补。附带效果是这套算子
从"给 QwQ-32B 定做"变成通用算子——K 可以是 1057、可以是奇数、最后一组可以只有 1 个元素。

**契约现在是：对外 K 任意；对内每个量化组补零到一个 int4 cube fractal（64 元素）。**
补零在 int32 上**精确**（不是近似），证明在 `int4_cube_lab/host/ragged_layout_test.cpp`。
QwQ-32B 在 TP=1..8 的全部八个行并行分片**补齐量都是 0**——raggedness 全在组层级，
碰不到 fractal 层级。

**kernel 侧已完成并全绿（62/62，`--stress 3`）**，单算子性能也验完了：对齐形状零退化
（≤2.1%，噪声内）、比旧路线快 1.23–2.78×、行并行 eff@4 从 0.25 到 0.54、精度 = P2 配置。

**但引擎级 TP 仍然不降延迟，而原因不在我们改的东西里。** `step_trace_time.csv` 把账
逐项对上了（D9）：TP=4 让 **Computing 减半**（6751 → 3275 µs/step，kernel 侧完全按预期
兑现），可是通信 3632 µs **`Overlapped = 0`**（一微秒都没重叠），外加 TP=1 本来就有的
5.3 ms 设备空闲。省 3476 − 加 3632 − 空闲涨 674 = **+829 µs**，与实测 step 增量完全相等。

**当天后半场把那两块都查到底了：**

1. **设备空闲不是我们的问题**（D12）：每步 5 个 host 停顿（最大 1.9 ms 在输入缓冲
   Fill 之前），**图没被切碎**，而且**空闲与 arm 无关**（BF16 4703 / W8A8 5021 /
   W4A8 5302 µs）。正确说法是"我们把计算做快了 2.6×，于是引擎的固定成本变成主项"。
   对症解是 vLLM 的 **`async_scheduling`（默认关）**，实测**我们这条 arm 1.23–1.29×**，
   一个开关、零 kernel 改动，且对 BF16 的领先从 2.08× 涨到 **2.28×**。⚠ 它**不支持 PP**。
2. **async 开着之后 TP 变成精确打平**（D13）：TP=4 8217 vs TP=1 8182 µs（差 0.4%），
   而 D9 的分解预测 (省 3476) − (加 3632) = +156 µs ≈ 0 —— **两种方法算出同一个 0**。
   ⇒ **挡在"打平"与"TP 真能用"之间的就是那 3632 µs 通信，消掉它值 1.78×。**
3. **fused op 开工调研**（D14）：in-kernel HCCL 原语齐全
   （`Hccl::AllReduce` + `Commit`/`Wait`，还有可直接访问对端显存的 `GetWindowsInAddr`），
   host 侧 context 也只是一个 comm name 字符串。当天判定「MC2 在这台机器上跑不起来」
   （`HcclAllocComResourceByTiling ret=4`）。

4. **⚠ D14 那个阻塞判定是错的，08-18 已推翻（D15）。** `ret=4` 是**一次性首调用**
   失败：第 1 次每个 rank 都挂、第 2 次每个 rank 都过，之后 **0/50**。world=2/4 都如此。
   `ret=4 = HCCL_E_INTERNAL`，**不是** `HCCL_E_NOT_SUPPORT=5` —— 这一条当天就够翻案。
   ⇒ **MC2 可用，两条路线都没被堵**（`Hccl::InitV2` 走同一条资源分配路径）。

5. **08-18 下半场（D17）**：**自研 all-reduce 算子写完了**，barrier 在 kernel 内
   （所以图里不需要 host 侧集合通信），多核靠"跨 rank 对称切分 + 每 block 一个旗标"，
   rank 内零同步。**TP=2/TP=4 六项门禁全过**（含 skew、200 次无 host barrier、
   24 张图同时存活），算子**原生吃 bf16**（GEMM 就是吐 bf16 的）而累加仍在 f32 里；
   定价 **解码档 16.9 µs vs HCCL 242–268 µs = 15×**（TP=2 是 22×）。
   ⚠ 两条边界：**TP=4 的 M=64 只是打平**（算法性的：我们的跨卡流量是 ring 的 2 倍，
   所以交叉点随 world 走），以及**引擎级还没验**。

6. **08-18 的落点（D15+D16），一句话**：**MC2 单跑绿、进 vLLM 必死**，所以厂商算子
   既定不了价也不能当存在性证明；**但我们自己写的跨卡 kernel 通了**，而且**完全不碰
   HCCL**（peer HBM 直读 + ACL IPC 映射）——30 形状逐位正确、400 次连跑、
   **NPUGraph 捕获重放结果正确**。⇒ **fused op 可以开工**，天花板仍是 1.78×。
   **开工前只剩一件事**：门禁里捕获失败过一次（放到进程最前面就成功），
   而 vLLM 要捕获很多张图，这条必须钉死，见 §2 第 3 项。

## 1. 已完成

### 1.1 布局契约：`int4_cube_lab/kernels/mg_kgeom.h`

硬件的真实粒度写在 `.inc` 里：fractal = 16 行 × C0，int4 的 C0 = 32 B = **64 元素**
（`kNzBlockSize = kK0B * kBlock`）。所以：

```
G       = ceil(K / GK)
n_g     = min(GK, K - g*GK)                 // 第 g 组真实元素数
n_g_pad = ceil(n_g / 64) * 64               // 补到 fractal
offset  = g * ceil(GK / 64)                 // 组起点，对每个 g 都成立
Kpad    = (G-1)*ceil(GK/64) + n_last_pad
```

**每组独立补齐**，所以每组都从 fractal 边界开始、含整数个 fractal —— kernel 里因此
不需要任何掩码，也不依赖 Mmad 对非对齐 k 的未文档化行为。

`GK % 64 == 0` 时只有末组可能补齐，且 ≤63 元素（<1%）。**GK 本身非对齐也正确**，
只是会逐组补齐（`GK=33/K=1057` 要补 99.8%）——**正确性普适、效率只在 GK 对齐时白拿，
这是两句独立的话。**

实测补齐量（`ragged_layout_test`）：

|--:|--:|--:|--:|--:|--:|
| 5120 / 2560 / 1280 / 640 | 1/2/4/8 | 5/3/2/1 | 1024/512/256/640 | =K | **0** |
| 27648 / 13824 / 6912 / 3456 | 1/2/4/8 | 27/14/7/4 | 1024/512/768/384 | =K | **0** |

### 1.2 为什么补零是精确的（这是整件事的支点）

补进去的 `q_a = 0`、`q_w = 0`，于是：

- Mmad 项 `Σ q_a·q_w`：补零贡献 **0**；
- 两个 rank-1 修正项 `w_ksum = Σ q_w`、`a_ksum = -Σ q_a`：补零贡献 **0**，
  **而且因为它们是在补零后的范围上求和的，所以没有任何地方需要记录"真实元素数"**；
- 末组 `scale = amax(|x|)/127`：补零不抬高绝对值的 max，**与不补零时逐位相同**。

`ragged_layout_test` 直接按 kernel 的算法（`.inc:369` 的
`((16*C_hi + C_lo) + 8*w_ksum − wz*a_ksum)`，Mmad 走**补齐后**的范围）解码 packed 载荷，
与定义式（真实范围的 `Σ A*(W−wz)`）逐个量化组比 **int32 精确相等**，
覆盖 K=1、n_last=1、奇数 K、非对齐 GK，零容差。**先在 host 上证明代数，再动 kernel。**

### 1.3 kernel 改动面（比预想的小）

关键简化：**短 slice 只可能是一个 L1 slab 的最后一个 slice。**
（`GK % 64 == 0` 时满组必然以满 slice 结束；不对齐时 `QGROUPS_PER_L1` 被钉成 1，
于是一个 slab 就是一个组。）所以冲刷条件只是一次比较：

```cpp
if (sInQ == SLICES_PER_QGROUP || s + 1 == slices) { /* flush */ }
```

**不需要跟踪任何组索引。** slab 边界永远是组边界，末组只是提前到达它。

其余改动：`numQGroups`/`Kb`/slab 几何运行期化；末 slice 的
`ndA/ndB.dValue`、`ldA/ldB.repeatTimes`、`mm.k` 取运行期短值（**这三个本来就是运行期
结构体字段**）；L1 保持统一 slice stride（短 slice 留洞），所以所有偏移仍是编译期常数、
零额外 DMA。`INNER_KB` 的定义从 `min(kSliceCap, GK/2)` 改成
`min(kSliceCap, ceilTo(GK,64)/2)` —— 对 GK ∈ {256,512,1024} **取值不变**，
但对任意 GK 也保证是 C0 的整数倍。

   日志 `int4_cube_lab/results/p65_mc2_engine.log`。

5. **🟡 把 drop-in 接进 vLLM 行并行路径** —— **2026-08-19 降为可选（D19）**：它在 DoD 之外，
   且不改变三方对比的结论。下面的施工说明保留，等交付矩阵出完再决定要不要做。
   （原文：D18 之后它比融合更该先做，86% vs 8%。）要做的：
   - 在 `MidGroupLinearMethod` 的行并行分支里，把 `dist.all_reduce` 换成

## 3. 决策与坑

> 编号是**稳定 ID**（正文和 memory 都在交叉引用），所以下面按**话题**分组而不是按号排：
> **ragged-K 本体** D1–D6、D8；**引擎级 TP** D9–D14；**继承自 P6** D7。

### D1 · 那个"未定位的机制"其实是 P0 的 GK 代价曲线，而且梯子答不出它

P6 D2 说行并行停滞"不是冲刷造成的（`nofix` 同样停滞），机制未定位，下一步必须是
dmaonly 梯子"。两点修正：

1. **量级早就量过。** `P0_COST.md` §5 是**固定 K、只变 GK** 的对照
   （o/M=16/K=5120：g1024 27.8 / g512 42.1 / g256 66.1 µs）。P6 的 TP 表把 K 和 GK
   一起变，所以分不开"字节少了"和"组变小了"；P0 那张表把它们分开了。
   决定性旁证在 P6 自己的 §1.3：**列并行 eff@2 0.92–1.07 / eff@4 0.77–1.06 几乎完美**
   ——列并行切 N，字节照样按 TP 减少，唯一区别是 **GK 没变**。
   ⇒ 不是"TP 缩放不了"，是**"GK 缩小"缩放不了**。
2. **dmaonly 梯子结构上答不出这个问题。** `midgroup_w4a8_gemm.inc:645` 起，
   `ABLATE_AIC_CFG >= 2`（dmaonly）**保留了每量化组一次的 CrossCore 握手往返**，
   `nofix`（`ABLATE_AIC_CFG=1`）和 `noaiv` 也都保留。每 tile 的握手次数
   `= numQGroups = K/GK`，**正是 `GK = 1024/TP` 精确钉死不变的那个量**。
   六个 `g{512,256}_dmaonly` build 跑完只会再读出一次平的地板。

教训与 P5 D6 同型但反向：那次是「机制解释属实 ≠ 它是主因」；这次是
**「消融梯子的每一级都保留了同一个不变量，那这把梯子问不出关于它的任何问题」**。
排消融实验前先问：**我要归因的那个量，在每一级上分别是多少？**

### D2 · 「不要做 ragged group」这条被推翻了 —— 记录为什么

`P6_TP.md` D1 和原 P6.5 都写着「不要投入 ragged group 支持，那是伪问题」，
理由是 `2^10 | 5120` 且 `2^10 | 27648`，`GK = 1024/TP` 恒整除。
**那个论证只在"接受 GK 随 TP 缩小"的前提下成立**，而这个前提本身就是问题的来源
（D1）。前提一撤，ragged 就从"没必要"变成"唯一不用付 GK 代价的路"。

同时它把两个包一起解了：**checkpoint 与并行度解绑**（原 D2 的部署问题——改 TP
不用重新量化模型），以及**算子从 QwQ-32B 专用变成通用**（很多模型的
`intermediate_size` 不是 1024 的倍数）。

**教训：一条"不要做 X"的结论，要连它依赖的前提一起记。** 前提变了，结论要重新过一遍，
否则它会以"已经论证过了"的身份挡住正确的路。

### D3 · `DataCopyPad` 的 `isPad=false` 会把 GM 里**紧随其后的真实数据**读进补齐区

`midgroup_quant_a.inc` 末组按行搬 `gReal * 2` 字节。`gReal=33` → 66 字节，
而 `DataCopyPad` 仍然搬整数个 32 B 块（96 字节），`isPad=false` 时多出来的 30 字节
**不是零，是同一行 GM 里第 33..48 个真实元素**。

症状极具误导性：`a_scale` **全过**（同分布再多 15 个采样，amax 在 bf16 下常常不变），
`a_hi`/`a_lo`/`a_ksum` 全错。修法是 `isPad=true` + `rightPadding = (ceilTo(bytes,32) − bytes)/2`。

**教训：`blockLen` 不是 32 B 整数倍的 `DataCopyPad`，`isPad` 必须为 true。**
而且这类 bug 的定性方法是**看哪些输出对了**——"scale 对、ksum 错"直接指向
"多读了同分布的数据"，而不是"算错了"。

### D4 · 改 `.inc` 不触发 kernel 重编 —— 会安静地拿旧 kernel 出数

`ascendc_library` 不追踪 `.cpp` 包含的 `.inc`。改完 `.inc` 直接 `make`，
**编译的只有 host，kernel 是旧的**，于是测试结果是旧 kernel 的。这一轮里
`isPad` 的修复第一次"没生效"就是这个原因。

`scripts/build.sh` 现在开头扫一遍：`.inc`/`.h` 比包含它的 `.cpp` 新就 `touch` 那个 `.cpp`
（实测对 20+ 个 wrapper 生效）。**凡是"改了源码但没重编"的可能，都要在构建脚本里堵死，
不能靠人记得。** 与 P6 D8 同型：一个安静地少做了工作的路径，和正常工作长得一样。

### D5 · harness 的参考实现用 `M` 而不是 `Mp` 取 `a_scale` 行距（既有 bug）

`ReferenceMidGroupGemm` 里 `a_scale_g[g*M + m]`，而 kernel 是用 `Mp` 启动的、按 `Mp` 取。
所以**只要 harness 补了 M（`M % TILE_M != 0`），参考就读错 scale**，读出来像 kernel 坏了：

| build | K | M | Mp | 结果 |
|---|--:|--:|--:|---|
| m128 | 5120 | 128 | 128 | PASS |
| m128 | 5120 | 64 | 128 | **FAIL**（mismatches=4690）|
| m16 | 5120 | 130 | 144 | **FAIL**（mismatches=9377）|

这在本期一开始把 ragged 的失败和 M 补齐的失败混在了一起。已加 `mp` 参数修掉。
**教训（与 `caller-invariants-hide-kernel-races` 同型）：门禁自己的不变量也要被检验**
——这个 bug 之所以活到今天，是因为所有既有调用点都恰好 `M % TILE_M == 0`。

### D6 · 参考全零时比较是**空过**，必须拒绝

`CompareBF16` 在误差能量为 0 时给 `snr_db = 999`（"逐位相同"），于是
**全零参考对全零设备输出会 PASS**。`mg_harness.h` 现在先数参考的非零元素，
不足 5% 直接 `REFUSING` 出数。`check_ragged.sh` 把 `REFUSING` 计为失败而非通过。

### D9 · 引擎级 TP 不降延迟，原因**已实测定位，且不在 kernel 里**

`sweep_p65_tp_engine.sh`（L=16、batch=1、`FULL_DECODE_ONLY`）的 step µs：

| arm | TP=1 | TP=2 | TP=4 | TP1→4 |
|---|--:|--:|--:|--:|
| BF16 | 20868 | 14506 | 12690 | **1.64×** |
| 我们 W8A8 | 12246 | 11959 | 11842 | 1.03× |
| 我们 W4A8 | 10045 | 10808 | **11589** | **0.87×** |

方向在 6 个测点上一致（TP=2 是 0.93/0.88/0.90，TP=4 是 0.87/0.87/0.84 @batch 1/16/64），
按 D11 的判据站得住。对 BF16 的领先从 2.08× 塌到 1.09×。

**`step_trace_time.csv` 把账逐项对上了**（µs/step，w4a8，profiling 开着所以绝对值偏大）：

| | Computing | Comm（未重叠）| **Overlapped** | Free | Stage |
|---|--:|--:|--:|--:|--:|
| TP=1 | 6751 | 0 | 0 | 5302 | 12053 |
| TP=4 | 3275 | 3632 | **0** | 5976 | 12882 |

1. **计算确实减半**（6751 → 3275，2.06×）。lab 预测 GEMM 4584→1814（省 2770 µs），
   实测 Computing 省 3476 µs，多出的 ~700 µs 是注意力头也随 TP 切了 —— 两边独立吻合。
   **kernel 侧做对了，ragged-K 的收益是真的。**
2. **`Overlapped = 0`** —— collective 一微秒都没和计算重叠，3632 µs 全在关键路径上。
3. **Free 那 5.3 ms 完全没动**（TP=1 就有，331 µs/层）。

净账：省 3476 − 加 3632 − Free 涨 674 = **+829 µs**，与实测 12053 → 12882 **完全相等**。

**两个可修项，排序清楚：**

| 问题 | 量 | 修好之后 |
|---|--:|---|
| 设备空闲（TP=1 就有）| 5302 µs/step | 单卡 10045 → 6751 µs = **1.79×**，不用多卡不改 kernel |
| collective 零重叠 | 3632 µs/step | TP=4 → 9251 µs = **1.30×** |

> **教训（与 P6 D7 同型）：并行度实验先问"每卡还剩多少活"。** 这次的版本是
> **先问"我要优化的那部分占 step 的百分之几"** —— 我们的 GEMM 只占 step 的 38%
> （占设备忙时的 68%），所以把它做便宜 2.5× 的上限就是 1.6×，而 TP 还要在上面
> 加自己的通信。Amdahl 先于 kernel。

### D11 · all-reduce 是**纯延迟受限**的，这决定了融合要怎么做

`npu_ops/python/bench_allreduce.py`，4 rank，两个设备组各扫一遍 payload：

| payload | devs 1,2,3,4 | devs 2,3,4,5 |
|--:|--:|--:|
| 10 KB | 258 µs | 271 µs |
| 640 KB | 268 µs | 265 µs |
| 2560 KB | 568 µs | 440 µs |

**10 KB → 640 KB：字节 ×64，时间 ×1.03。** 在**解码 payload 上**贵的不是线，
是**每次调用的固定开销**。（microbench 的 265 µs 含 eager dispatch；图内引擎实测
113 µs。两者都是延迟。）

**⚠ 关于选卡，我第一版的结论下错了，改正记在这里：**

我看到 10 KB 那一行两组一样，就写了"拓扑不是原因、别再查"。两个错：

1. **那两组设备（`1,2,3,4` 和 `2,3,4,5`）其实都是跨组的**（边界在 logic 3/4），
   所以我是拿两个落在同一侧的配置去否证一个区分 —— 实验根本没覆盖组内的情形。
   而且 device 0 挂死，**TP=4 在组内凑不出 4 张卡**，所以这台机器上 TP=4 必然跨组。
2. **2560 KB 那一行两组是不一样的，我当噪声扔了**：
   `1,2,3,4` 是 568 µs / 6.92 GB/s，`2,3,4,5` 是 440 µs / 8.94 GB/s，**1.29×**。
   用户给的机器模型解释得通：**两组各四卡、各有自己的带宽域，均衡跨组（2+2）能同时
   吃到两组带宽，而 3+1 或组内只能吃一组** ⇒ 跨组反而可能翻倍带宽。

**用 TP=2 做的干净对照（TP=4 做不到：device 0 挂死，组内凑不出 4 张）**，
10240 KB / ring 带宽：

| 设备 | 组关系 | 10 MB | ring 带宽 |
|---|---|--:|--:|
| 1,2 | 组内 {0–3} | 927 µs | 11.31 GB/s |
| 2,3 | 组内 {0–3} | 927 µs | 11.31 GB/s |
| 4,5 | 组内 {4–7} | 928 µs | 11.30 GB/s |
| **3,4** | **跨组** | **521 µs** | **20.14 GB/s** |

三个组内配置落在 11.30–11.31 GB/s（紧到不像巧合），唯一跨组的是 **1.78×**。
**逻辑分组确认为 {0,1,2,3} / {4,5,6,7}。** 而 10 KB 上四种配置都是 ~175 µs。

**正确的表述（三句都要在）：**
- **解码 payload（10 KB）是延迟受限 ⇒ 选卡无关**，TP 的解码罚金换设备治不了；
- **≥2.5 MB 是带宽受限 ⇒ 选卡有关**：组内 11.3 GB/s vs 跨组 20.1 GB/s = **1.78×**；
- **这条打在我们最弱的环节上**：行并行的 all-reduce 是 `[M, hidden]`，**prefill 的
  M 是几千**（M=2048 → 20 MB，牢牢在带宽区），而 D13 定的正是 prefill 我们输
  0.64–0.69×。**prefill 侧的 TP 一定要挑均衡跨组的设备集**；TP=4 用 `2,3,4,5`（2+2）
  而不是 `1,2,3,4`（3+1），2560 KB 上 1.29×。

**这条数据直接判掉了一种融合设计：**

- ❌ **分块流水**（`npu_mm_all_reduce_base` 的做法：沿 N 切 C 块，用块 i 的通信盖
  块 i+1 的计算）。在这台机器上**每块都付满 113 µs**，C=4 就是 452 µs 通信而不是
  113 —— 原本要藏 113，现在要藏 452。**分块把问题放大。**
  第二个独立理由：batch=1 解码时层内是严格串行链
  （qkv → attn → o_proj → AR → residual+norm → gate_up → silu → down_proj → AR），
  **没有独立工作可以藏**。
- ✅ **消掉那次调用**：一个 fused op，让我们的 GEMM 在 epilogue 里直接做跨 rank
  归约，不再有独立的 HCCL launch。先例是 CANN 自己就把 matmul+all-reduce 做成了
  单 op，所以底层原语存在；我们要做的是同一类，只是把 matmul 换成 mid-group W4A8。
  天花板：comm 3632 → 0 ⇒ TP=4 的 step 12882 → 9251 µs = **1.30×**
  （与"完美重叠"同值，因为在这里"消掉"和"完全藏住"等价）。

顺带解释了一个已测到的现象：payload 到 640 KB 都免费 ⇒ **collective 的每 token 成本
随 batch 下降**，所以 w4a8/w8a8 的 TP 罚金在 batch=64 时收窄（0.997 vs batch=1 的 0.979
反过来了 —— 那是 GEMM 占比同时在变，两个效应叠加，不要单独归因）。

### D12 · 那 5 ms 空闲是**引擎每步的 host 开销，与 arm 无关**，图没有被切碎

我先前的推断（"331 µs/层，与 PIECEWISE 税同量级，所以解码步大概没跑成一整块图"）
**是错的**，`kernel_details.csv` 的 gap 结构直接推翻它：

| gap 大小 | 个数 | 总计 | 占空闲 |
|---|--:|--:|--:|
| <10 µs | 12697 | 13.7 ms | **4.0%** |
| 50–200 µs | 271 | 29.8 ms | 8.8% |
| 200–1000 µs | 287 | 132.8 ms | 39.2% |
| >1000 µs | 83 | 153.4 ms | **45.3%** |

图被切碎的话应该是 ~1000 个 ~330 µs 的 gap；实际是 **370 个大 gap 占 84.5%**，
而 12697 个小 gap 只占 4%。**一个中位步**（257 个 kernel，span 10786 = busy 6735 +
idle 4050 µs）里，**5 个 >100 µs 的 gap 占了 3684 µs（91%）**：

| gap | 之后紧跟的 kernel | 是什么 |
|--:|---|---|
| **1889 µs** | `aclnnInplaceFillScalar_Fill` | 填输入缓冲 |
| 653 µs | `aclnnInplaceFillScalar_Fill` | 同上 |
| 490 µs | `FusedInferAttentionScore` | 注意力前 |
| 444 µs | `aclnnIndexSelect_GatherV3` | 取 block table |
| 209 µs | `aclnnIndexSelect_GatherV3` | 同上 |

全是 vLLM 的 scheduler / sampler / 输入准备，**绝大部分在模型 forward 之前**。

**决定性的一步是量 BF16 —— 空闲与 arm 无关：**

| arm | Computing | **Free** | step | Free 占比 |
|---|--:|--:|--:|--:|
| BF16 | 17806 | **4703** | 22626 | 21% |
| 我们 W4A8 | 6751 | **5302** | 12053 | **44%** |

绝对值一样，占比差一倍。⇒ **这不是我们引入的**，正确的说法是：
**我们把计算做快了 2.6×，于是引擎的固定 host 成本变成了我们 step 的 44%。**

**对症的开关是 `async_scheduling`**（vLLM 的 `SchedulerConfig`，默认 `False`，文档写的
就是 "helps to avoid gaps in GPU utilization"）—— 把 host 准备与上一步的 forward 重叠。
已加 `bench_engine_decode.py --async-scheduling`。**实测生效，是本期最大的一笔收益：**

| arm | batch | async 关 | async 开 | 加速 |
|---|--:|--:|--:|--:|
| **我们 W4A8** | 1 | 10045 | **8182** | **1.23×** |
| **我们 W4A8** | 16 | 12124 | **9430** | **1.29×** |
| BF16 | 1 | 20868 | 18687 | 1.12× |
| BF16 | 16 | 24850 | 21634 | 1.15× |

**一个开关、零代码、零 kernel 改动**，而且**帮我们比帮 BF16 多**（1.23× vs 1.12×）——
因为空闲在我们 step 里占比更大。副作用：**对 BF16 的领先从 2.08× 涨到 2.28×**
（18687/8182），batch=16 是 2.29×。3.3 ms 空闲里 async 吃掉约 1.9 ms，
剩下 8182 − 6751 ≈ 1.4 ms 是重叠不掉的部分。

**⚠ `async_scheduling` 不支持 PP** —— P6 那条已交付的 PP 路线用不了它，这是
PP 与 TP 之间新增的一条不对称，选部署形态时要算进去。

### D13 · async 开着之后，TP 变成**精确打平** —— 这是 D9 那笔账的独立验证

| w4a8, async 开 | TP=1 | TP=4 |
|---|--:|--:|
| batch=1 | 8182 | **8217（1.00×）** |
| batch=16 | 9430 | 11102（0.85×）|

**去掉 idle 项之后，TP=4 与 TP=1 在 batch=1 上完全相等**（差 35 µs = 0.4%）。
而 D9 的分解预测的就是 (GEMM 省 3476) − (通信加 3632) = **+156 µs ≈ 0** ——
两个数都在噪声内，**用完全不同的方法算出同一个 0**。

**这让 fused op 的价值定性变了**：TP 现在不是"亏"，是**精确打平**，而挡在
"打平"与"TP 真的有用"之间的就是那 3632 µs 通信。消掉它 ⇒ 8217 − 3632 ≈ 4.6 ms
⇒ **对 TP=1 是 1.78×**（而不是先前估的 1.30×，因为基线已经被 async 压低了）。
**fused GEMM+all-reduce 从"挽回亏损"升级成"TP 能不能用的唯一开关"。**

batch=16 仍然输（0.85×）：那里 GEMM 占比更小而通信照付，方向与 §5 的大 M 一致。

> **L=16 会系统性放大这个问题**：空闲是**每步**固定的，不随层数增长，所以真实的
> 64 层模型上设备活儿是 4 倍而空闲不变 ⇒ 占比从 44% 降到约 17%。
> **引用这 44% 必须带上 L=16 这个限定。** 反过来，TP 的那笔交易（GEMM 省 vs 通信加）
> 两边都随 L 线性，所以 D9 的 TP 结论在 L=64 上不变。

### D14 · fused GEMM+all-reduce 开工调研：**原语齐全，但 MC2 在这台机器上跑不起来**

按"不猜先探"的规矩，开工第一步不是写 kernel，是查原语和定价。三个结果：

**(1) in-kernel HCCL 原语存在，而且比预想的强。**
`$CANN/aarch64-linux/asc/include/adv_api/hccl/hccl.h` 有 `class Hccl`：

```cpp
Hccl hccl;  hccl.InitV2(context, initTiling);
auto h = hccl.AllReduce(sendBuf, recvBuf, count, dtype, op);
hccl.Commit(h);        // 通知通信侧开跑
hccl.Wait(h);          // 需要结果时才等（Commit/Wait 解耦 = 可以真重叠）
hccl.Finalize();
```

**更关键的是 `GetWindowsInAddr(rankId)` / `GetWindowsOutAddr(rankId)`** ——
文档写的是 "Windows addr is **shared by all ranks** in the same comm group"，
即**内核内直接访问对端显存**。于是有两条设计，而**第二条才贴合 D11 的测量**：

| | 做法 | 10 KB 上的预期 |
|---|---|---|
| A | `Hccl::AllReduce` + `Commit`/`Wait`（托管，走通信服务）| 省掉 op launch，但仍走 task/msg 机制 |
| **B** | `GetWindowsInAddr` 拿对端缓冲 + `QueueBarrier` + 自己在 AIV 里归约 | **完全没有 HCCL task**。TP=4 读 3×10 KB = 30 KB，成本只剩 barrier |

D11 说贵的是**机制不是线**，所以 B 才是对症的。
另外 `AllReduce` 有 `repeat>1` 参数，那正是**分块流水**的接口——**显式不要用**。

**(2) host 侧的 context 不用自己造。** `npu_mm_all_reduce_base` 的签名是
`(Tensor x1, Tensor x2, str hcom, *, ..., dequant_scale, pertoken_scale, antiquant_*)`
—— 通信域就是一个**字符串 comm name**，
`pg._get_backend(torch.device("npu")).get_hccl_comm_name(rank)` 一行拿到
（vllm-ascend 的 `linear_op.py:457` 就这么用）。范式现成。

**(3) ⛔ 但 MC2 在这台机器上跑不起来 —— 这是当前的硬阻塞。**
`npu_ops/python/bench_fused_allreduce.py`（本想用 CANN 自带的融合算子给我们的项目
定价，不写一行 kernel）在 4 rank 上必然失败：

```
aclnnQuantMatmulAllReduceV2 failed, error code is 561000
Nnopbase fails to invoke the HcclAllocComResourceByTiling ... ret = 4
```

试过 `HCCL_BUFFSIZE=200`、`HCCL_OP_EXPANSION_MODE=AIV`，**都不行**。

**为什么这个结果值钱**：我们自研的 in-kernel `Hccl::InitV2` 会走**同一条**
`HcclAllocComResource` 路径，所以这个阻塞会原样挡住我们。**在一个下午发现它，
比写三天 AscendC 之后发现强得多。** 顺带一个巧合（不作因果断言）：
`VLLM_ASCEND_ENABLE_MATMUL_ALLREDUCE` 默认关着（D10）。

**⇒ fused op 的第一个任务不再是写 kernel，而是：让这台机器上跑通任何一个 MC2 算子。**
在那之前，写 kernel 的每一步都建立在一个没验证的假设上。

### D15 · D14 的阻塞判定是错的：`ret=4` 是**一次性首调用**失败，重试即过

按 D14 的交代，08-18 第一件事是"让 MC2 通"。结果是**它本来就通**：

| | 结果 |
|---|---|
| 第 1 次 `npu_mm_all_reduce_base` | **每个 rank 都失败**（`HcclAllocComResourceByTiling ret=4`）|
| 第 2 次 | **每个 rank 都成功** |
| 之后 50 次 | **0 失败** |

world=2 和 world=4 同样的模式。`HCCL_BUFFSIZE` / `HCCL_OP_EXPANSION_MODE` 不是原因——
它们从来没参与过。

**当天就摆在眼前的反证，没被读出来**：`ret=4` 在 `hccl_types.h` 里是
`HCCL_E_INTERNAL`，而 `HCCL_E_NOT_SUPPORT` 是 **5**。"这台机器不支持 MC2" 这句话
对应的返回码不是 4。**先查错误码的语义，再下能力性结论。**

**为什么它伪装得像"必然失败"和"形状相关"**：每个探针都是新进程 → 每次都撞首调用；
而一旦在两次 MC2 尝试之间插入**任何别的集合通信**（`dist.barrier()`、
投票用的 `all_reduce`），重试就不再生效，失败看起来就变成"逐 rank 偶发"、
"M=1 必挂"。**是观测手段本身制造了那个假象。** 正确的重试协议是：
连着调两次，中间什么都不放（`bench_fused_allreduce.py:_lockstep`，那里记了三种写法
里为什么只有这一种work）。

**教训（与 [[caller-invariants-hide-kernel-races]] 同型）：在宣布一个能力缺失之前，
把同一个调用**再跑一次**。** 一个"首次"失败，在每个探针都从冷进程起步的情况下，
和"永远"失败长得完全一样。附带的第二条：**为了观察 bug 而加的同步，可能就是 bug 的
成因**——barrier 是用来对齐的，这里它恰好破坏了要观察的那次资源分配。

**⇒ 但真正拦路的东西换了一个：MC2 单跑没问题，进了 vLLM 就挂。**

在引擎上开 `VLLM_ASCEND_ENABLE_MATMUL_ALLREDUCE=1`（BF16 arm、TP=4、`--async-scheduling`）：

| 做法 | 图模式 | 结果 |
|---|---|---|
| 直接开 | FULL_DECODE_ONLY | 第一个行并行层 `aclnnMatmulAllReduce` 打死 worker（vLLM 没重试）|
| 算子上包一层重试 | FULL_DECODE_ONLY | **还是死** —— 失败落在图捕获里，catch 不回来 |
| 把首调用烧在 `get_hcomm_info`（layer 构造期，早于捕获）| FULL_DECODE_ONLY | warmup **四 rank 全 `ok after 2 attempt(s)`**，不再崩；**挂死在图捕获，1800 s 超时** |
| 同上 | **`--eager`（完全不捕获）** | warmup 同样全过，**仍然挂死**：`RPC call to sample_tokens timed out` |

**最后一行推翻了"是图捕获的锅"这个中间结论**（我先写过一版，作废）。
去掉捕获它照样挂 ⇒ **MC2 是在真实 forward 里挂的**。
对照组两边都正常：flag 关时 FULL_DECODE_ONLY 9.3 ms、eager 33.3 ms，都跑完。

**机制未定位**，最像的一条：`HcclAllocComResourceByTiling` 是**按 tiling** 分配的，
而单算子 microbench 只有一两个 tiling（"失败一次再重试"就够），真实模型里
16 层 × 2 个行并行层 = 几十个不同 tiling，每个都要重新分配一次。**不作断言。**

**所以现在的事实是三句，要一起讲：**
1. **MC2 单独跑是好的** —— 4 rank、两种 dtype、上百次迭代、稳定（D15 上半段）；
2. **MC2 在这个 vLLM 引擎里跑不起来** —— 崩或挂，与图模式无关，首调用失败吸收掉了也一样；
3. **所以"用厂商 MC2 零成本给融合定价"这条路是死的**，它既定不了价，也不能作为
   "自研 in-kernel Hccl 算子能在引擎里活下来"的存在性证明。

**对自研 fused op 的影响（这才是要带走的）：**
天花板还是 1.78×（3632 µs），没变。但**开工前的门禁多了一条**，而且比 D14 那条更贴近失败点：
**先证明一个带 in-kernel `Hccl` 的自研算子能在 16 层规模的真实 forward 里连续跑几十步不挂**
（不只是 microbench 跑通），**并且能被 `torch.npu.NPUGraph` 捕获重放**——
因为解码侧的全部收益都建立在 `FULL_DECODE_ONLY` 上，实测退回 PIECEWISE 是
9.3 → 16.0 ms，**比要省的 3.6 ms 大得多**。
**⚠ 我先写过"方案 B 可能根本不碰 `HcclAllocComResource`"，那句是错的，作废。**
查了 `adv_api/hccl/hccl.h`：`GetWindowsInAddr(rankId)` 是 **`class Hccl` 的成员**
（h:365），要先 `InitV2(context, initTiling)`（h:278），而那个 `context` 正是 host 侧
`HcclAllocComResourceByTiling` 产出的 `contextAddr`。**所以 A 和 B 都要走资源分配这一层。**

正确的分层是：

| 层 | 方案 A（`AllReduce`+`Commit`/`Wait`）| 方案 B（`GetWindowsInAddr`+`QueueBarrier`）|
|---|---|---|
| host 侧 `HcclAllocComResource` → `InitV2` | 要 | **要**（这条是共用的失败面）|
| 每次通信下发 task 给 HCCL server（队列）| 要 | **不要**（直接读对端 window）|

MC2 挂在哪一层**未知**。所以 B 的价值不是"绕开失败面"，是"**少一层**"：
如果挂的是队列/msg 机制，B 躲得开；如果挂的是资源分配，B 一样挂。

**我们相对 MC2 真正的结构性优势在别处**：MC2 的分配是 **`ByTiling`** 的，一个真实模型
里几十个不同 tiling 就要分配几十次；而**我们的 tiling 由自己定，可以每个通信域只分配
一次并全程复用**。这是可以主动设计掉的一个失败源——**但仍是假设，要在第 2 项里验。**

**顺序：先做最小算子验 (a)(b)，B 优先（少一层，代价也更低）。**

**引擎基线（BF16 / TP=4 / async / L=16 / batch=1）**：
FULL_DECODE_ONLY 9305 / 9691 / 9041 / 10021 µs（均值 ~9.5 ms，散布 10%，在 ±15% 噪声带内）；
PIECEWISE 15987 µs；eager 33270 µs。**图模式本身值 1.7×，比通信这笔账大。**

**定价的现状（分清哪个数能用）：**

- **eager 口径，可用来判"路径通不通"，不可用来判"融合值多少"**（六个测点全出，
  两条路数值一致）：

  | shape | M | split | fused | 省 |
  |---|--:|--:|--:|--:|
  | o_proj TP=4 | 1 | 451.7 | 373.4 | 78.3 |
  | o_proj TP=4 | 16 | 458.6 | 394.9 | 63.7 |
  | o_proj TP=4 | 64 | 457.6 | 408.7 | 48.9 |
  | down_proj TP=4 | 1 | 457.1 | 422.6 | 34.5 |
  | down_proj TP=4 | 16 | 457.6 | 432.3 | 25.3 |
  | down_proj TP=4 | 64 | 469.5 | 440.6 | 28.9 |

  eager 下拆分付两次 dispatch、融合付一次，**省的主要是 python**
  （见 memory `npu-eager-bench-is-host-bound`）。

- **图内口径在这台机器上做不出来**：`torch.npu.NPUGraph` 捕获普通
  `dist.all_reduce` **必挂**（四 rank 停在 "Waiting for pending NCCL work to finish
  before starting graph capture"，20 分钟不返回）。所以 `--graph` 默认关。
  **这不值得在 microbench 里修**——vLLM 在 `FULL_DECODE_ONLY` 下本来就能正确捕获
  collective，所以**引擎才是回答图内问题的仪器**，见 §2 第 2 项。

### D16 · 自研跨卡 kernel 通了 —— 而且**不需要 HCCL 的任何一层**

D15 把门禁定成两问（能否被 NPUGraph 捕获、能否在真实规模连跑）。答案：**都能**。
路线是 peer HBM 直读，**没有 `Hccl` 对象、没有 `InitV2`、没有通信资源分配、没有任务队列**
—— MC2 死在里面的机制一个都没碰。

| 门禁 | 结果 |
|---|---|
| `enable_peer_access` 4 卡两两 | ✅ 全通，含跨 {0-3}/{4-7} 组边界的 3↔4 |
| 30 个不同 shape 的 all-reduce | ✅ **30/30 逐位等于 `dist.all_reduce`** |
| 400 次连续迭代 | ✅ 不挂 |
| **NPUGraph 捕获 + 重放** | ✅ **world=4，out=10.0 正确**（1+2+3+4）|

产物：`npu_ops/kernel/peer_read_sum_f32.cpp`、`npu_ops/host/{peer_read_sum,peer_ipc}.cpp`、
`npu_ops/python/test_peer_allreduce.py`、`results/p65_peer_allreduce.log`。

**路上踩到的四个坑，每一个都会咬下一个人：**

1. **裸 `data_ptr()` 当对端地址是静默错误。** 四个 rank 的地址**数值完全相同**
   （`0x12c041200000`），`aclrtDeviceEnablePeerAccess` 对所有配对都返回成功，
   但 kernel 读的是**自己的内存**——不 fault，只是答案错。症状是算术性的：
   `world × 自己的值`。⇒ 必须用 `aclrtIpcMem{GetExportKey,SetImportPid,ImportByKey}`
   做真映射，并**断言映射后的地址两两不同**。见 memory `no-cross-device-uva-on-ascend`。
2. **AscendC 里运行期下标索引局部指针数组会静默塌缩成 `[0]`。**
   `GM_ADDR peers[8]={p0,...}; peers[r]` 恒等于 `p0`。它伪装成"跨卡读不work"——
   而**一次只传一个指针会通过**，因为那条路只碰下标 0。⇒ 展开，不要用运行期下标。
   定性方法还是老的那条：**看哪些配置对了**。
3. **导出的 IPC key 是跨进程存活的有限资源。** 给 30 个 shape 各导一次、进程又死了没关，
   下一轮第一次 `aclrtIpcMemGetExportKey` 就 `507899`。⇒ 一个常驻 staging buffer
   **只导一次**（真实算子本来就该这样），并且退出时 `ipc_close`。
4. **torch_npu 自带的 `acl_rt.h` 比 CANN 8.5 旧**，没有 IPC API，而且在 include 路径上
   排前面 ⇒ 编译报 "was not declared in this scope"。符号 `libascendcl.so` 是导出的
   （`nm -D` 验过），所以自己 `extern "C"` 声明，别去跟 include 顺序较劲。

**捕获这条的最终状态（`test_peer_graph_order.py`，在已知能work的骨架里逐轴加）：**

| 轴 | 结果 |
|---|---|
| A 直接捕获 | ✅ 稳定（另有 3 次独立复现 12/12）|
| B 先跑 1 / 30 / 400 次再捕获 | ✅ **全过** |
| C 捕获→跑→再捕获（交错）| ✅ |
| D 同进程保活多张图（8 张）| 🟡 **偶发**：加 barrier 后 13 / 13 / 12（13 = 全过）|

**两个被否掉的假设，都是我先下的结论，记下来免得再犯：**

1. ~~"前序活动会让捕获失效"~~ —— **B 直接否掉**，跑 400 次再捕获照样过。
   最初那次失败（`MTE address out of range`）出现在一个自带别的机制的 harness 里，
   **不能归因到它想测的那条轴**。
2. ~~"每进程存活图数有上限，约 11–12"~~ —— **不是上限，是偶发**：三次跑出 11 / 13 / 5。
   真差别是 **D 的循环里漏了 `dist.barrier()`**，而 A/B/C 每步都有。补上之后
   变成 13 / 13 / 12。

**⚠ 仍未收口**：补了 barrier 之后 D 还有约 1/3 的概率在最后一张图上失败
（`the model stream execute failed`，注意**不是**最初那个 MTE 越界，是另一个错误）。
**vLLM 的 `FULL_DECODE_ONLY` 要捕获几十张图，所以集成前必须把这条追到底。**
但它**不阻塞写 kernel**：算子本身的正确性和可捕获性已经证实。

> **今天第三次栽在同一类错误上**（D15 的"逐 rank 偶发"是 barrier 造成的、
> `_lockstep` 的投票 `all_reduce` 打坏了 MC2 重试、现在是 D 循环漏 barrier）。
> **教训固化成一条规则：多 rank 实验里，任何"偶发/与次序有关"的现象，
> 先怀疑自己的同步，再怀疑平台。** 而且**每加一个同步点，都要问它会不会
> 改变被测对象**——barrier 既能消除假象，也能制造假象。

### D17 · 自研 all-reduce 算子写完了：barrier 进 kernel、多核、bf16 原生，比 HCCL 快 15×

D16 的探针靠**调用方** `dist.barrier()` 同步，而捕获图里不能有 host 侧集合通信 ——
所以 §2 第 5 项把"in-kernel barrier"列为 D16 之后第一件要写的东西。写完了，
并且顺手把定价做了，因为**"正确"不等于"值得上"**。

**协议（put-nothing / read-everything）**：每个 rank 只写自己的 staging、只读别人的。
`seq = ++本地计数器` → `slot = seq & 1` → 拷 x 进自己的 slot → **刷 cache** →
发布 seq → 自旋等所有 peer 的 seq → 读所有人的 slot 求和。三个设计点各有理由：

- **两个 slot 就够**：rank 只有过了 seq+1 的 barrier 才能到 seq+2，而 peer 发布 seq+1
  发生在它读完 seq 数据之后 ⇒ 覆盖 slot 时没人还在读它。一个会 race，三个白给。
- **计数器必须在设备内存里**：图捕获会把 kernel 参数冻住，host 传的 seq 在每次重放里
  都是同一个值，barrier 会**永远立刻通过**（看起来对，skew 一来就错）。
- **刷 cache 的顺序**：数据的 flush 必须在旗标的 flush 之前，否则 peer 看见旗标时
  可能看不见数据。

**多核不需要任何 rank 内同步**（第二版）：把切分做成**跨 rank 对称**的 ——
`sliceElems` 只由 `n` 推出（host 侧 `slice_elems_for`），所以四个 rank 不用通信就切得
一模一样；于是**旗标按 block 分**，block b 只等 peer 的 block b。整件事变成
`usedBlocks` 个并行的独立 barrier，block 之间**根本不需要知道彼此**。
切片按 512 B 对齐，避免两个 block 共享 cache line（一个 block 的 flush 会打另一个的
staging）。

**门禁（`test_peer_barrier.py`，6 项，TP=2 与 TP=4 各一遍全过）**

| 项 | 为什么它才算数 |
|---|---|
| 1 lockstep | **不算数**，写在这里是为了说明它不算数：barrier 完全坏掉也能过 |
| 2 skew 25 ms/rank | 快的 rank 会读到慢的 rank 还没写的 slot |
| 3 skew + 每步换值 | 读到**上一步**的数据变成可见错误，而不是巧合正确 |
| 4 200 次随机 skew、**无 host barrier** | ✅ |
| 5 捕获 + 20 次重放 | ✅ 每次重放都是新一轮 seq，barrier 在重放里也得工作 |
| 6 **24 张图同时存活** | ✅ 这就是 §2 第 3 项那条未收口的轴，见下 |

**六项门禁 f32 与 bf16 各跑一遍，TP=2/TP=4 都过。** ⚠ bf16 的测试值必须**在 bf16 里
精确**（这里用 0.25 的倍数、和 <64）：原来的 `(rank+1)*1000+step` 求和是 10000，
**bf16 表示不了**，于是"错"全是 rounding，门禁对 barrier 什么也证明不了。

**bf16 是主格式，不是 f32**（第三版，用户 2026-08-18 指出）。f32 是从 D16 探针
**继承**来的，不是选出来的 —— 而 `midgroup_w4a8_gemm.cpp:107` 的输出 `y` 就是 bf16，
vLLM 的残差流也是 bf16。f32 版本等于在每次调用两端各加一次 cast，而且**跨卡字节翻倍**。
bf16 版本三件事一起解决：

- **过网字节减半** —— 大 M 那笔亏就是从这儿来的；
- **累加仍然在 f32 里**（UB 里 `Cast` 上去、求和、出口只 round 一次）⇒
  **比它替换掉的 bf16 集合通信更准**，不是更差；
- staging 布局按 f32 单位算容量，所以**同一个映射一次的 buffer 两种 dtype 通用**
  （不用再导 IPC key，避开 D16 那个 507899）。

两个入口 `peer_allreduce_{f32,bf16}` 由同一个模板 body 生成（一个 .cpp 里两个
`__global__`，工具链会各生成一份 launch stub），host 按 `x.scalar_type()` 派发。
⚠ 32 B 的 DataCopy 块 = 8 个 f32 **但 16 个 bf16**，所以对 f32 合法的形状对 bf16
可能非法；对齐、切片、`kMinSlice` 全部改成**按字节**算。

### D18 · 融合的定价做完了：**融合最多再省 ~10 µs/call，而 drop-in 已经拿了 ~98 µs**

§2 第 5 项的方向是"在 GEMM epilogue 里做跨 rank 归约"。动那个 63 KB、背着 62 项门禁的
kernel 之前，先量一件事：**把 D17 的算子直接插在 GEMM 后面（drop-in），和真融合，
差多少？** 三个臂都是**同一种口径**（捕获图、重放、wall/次），所以彼此可减：

TP=4，真实行并行形状，µs/call（`bench_fused_layer.py`，barrier 地板 14.7 µs）：

| 层 | M | gemm | +ours | **marginal** | local(world=1) |
|---|---|---|---|---|---|
| o_proj (K=1280) | 1 | 27.6 | 42.9 | **15.3** | 10.8 |
| o_proj | 16 | 27.2 | 112.0 | **84.7** | 9.8 |
| o_proj | 64 | 33.2 | 313.4 | **280.2** | 12.4 |
| down_proj (K=6912) | 1 | 42.3 | 57.4 | **15.1** | 7.8 |
| down_proj | 16 | 42.4 | 120.0 | **77.6** | 10.1 |
| down_proj | 64 | 50.2 | 340.3 | **290.0** | 13.2 |

`marginal` = (gemm+ours) − gemm，就是我们的 all-reduce **在真实层里**的边际成本
（与 D17 单算子的 16.9 / 77 / 280 逐点吻合 ⇒ 两个口径互证）。
`local` = 同一个算子跑 **world=1**：一样的本地流水（读 y → 写 staging → 读回 → 写 out
= 4n 本地流量），**零跨卡流量、零等待**。

**这张表的三个读法，第二个直接决定了要不要融合：**

1. **`local` 几乎不随 M 变**（7.8 → 13.2 µs，而字节涨了 64 倍）⇒ 本地拷贝在 HBM 上
   接近免费（M=64 那档 4n = 2.6 MB / 13.2 µs ≈ 200 GB/s）。**M=64 的 290 µs 里
   几乎全是跨卡流量**（3n ≈ 2 MB / 280 µs ≈ 7 GB/s，正是 D17 量到的 fabric 带宽）。
   **融合搬不动跨卡那部分。**
2. **M=1 那档 `marginal`(15.3) ≈ barrier 地板(14.7)** ⇒ 解码档的成本**几乎全是固定
   开销**（barrier + 一次 launch），payload 只占 ~0.6 µs。
3. ⇒ **融合能删掉的只有两样**：一次 kernel launch（~4 µs）和 **y 过一次 GM 的往返**
   （GEMM 写 y、算子再读回来；融合版直接把 tile 写进 staging）=`local` 的一半，
   4–7 µs。**合计 ≤ ~10 µs/call，而且在每个 M 上都是这个量级。**

**换算成决策**（用引擎 profile 的保守口径 113 µs/call，而不是 microbench 的 250）：

| 做法 | 每次省 | L=16 × 2 = 32 次/step | 占那 3632 µs 的 |
|---|---|---|---|
| **drop-in**（`dist.all_reduce` → 我们的算子）| ~98 µs | **~3.1 ms** | **~86%** |
| **再融合进 epilogue** | ~10 µs | ~0.3 ms | ~8% |

⇒ **先做 drop-in 进 vLLM 并在引擎上量，不要为了 8% 去动那个 63 KB 的 kernel。**
这不是"融合没用"，而是**融合的收益被 D17 自己吃掉了**：barrier 一旦降到 15 µs，
剩下能省的就只有一次 launch 和一次本地往返。

**如果以后要融合，设计已经清楚，不用重想**：行并行的输出形状在各 rank 上完全一致，
所以 GEMM 的**输出 tile 划分本身就是跨 rank 对称的** —— 让 block b 写完自己的 tile 后
发布 tile b 的旗标、再归约 tile b，**和 D17 的多核切分是同一个技巧**，rank 内依然
不需要任何同步。真正的新问题只有一个：GEMM 是 AIC+AIV 混合的，而归约是 AIV 的活，
要决定 epilogue 挂在哪一侧。

**顺带一个正确性结果**：六个真实形状（两层 × 三个 batch，输入是**真的 GEMM 输出**
而不是常数）全部**逐位等于 f32 累加后 round 一次的参考**。D17 的门禁用的是人造值，
这一条是在真实数据分布上补的。

**口径提醒**：表里的 eager 三列（gemm 57–66 / +hccl 300–323 / +ours 114–146 µs）
只用来看方向，**不能和捕获列相减** —— eager 下我们的算子是 host-bound（D17 已量：
发起就要 25 µs），HCCL 是设备受限。**两种口径不能混着算账。**

### D10 · 排除掉的四个"是不是我们没做对"

按顺序排掉的，每条都有实测依据，不要重新怀疑（第 4 条**只对解码成立**，见 D11）：

1. **我们的 op 进不了 ACL graph** → ❌。`--eager` 31003 µs vs graph 10045 µs = **3.09×**，
   捕获是生效的（fake kernel 已注册、host op 里没有同步）。
2. **那笔开销在 host 侧** → ❌。捕获生效后 dispatch 不在关键路径；profile 里它是
   `Communication` 和 `Free`，都是设备侧的量。
3. **BF16 走了 matmul-allreduce 融合而我们没走** → ❌。
   `VLLM_ASCEND_ENABLE_MATMUL_ALLREDUCE` 默认 `'0'`，**对所有 arm 都关着**。
   BF16 的 TP 加速纯粹来自它 GEMM 占比大。（而且 D14 发现那个融合在这台机器上
   根本跑不起来——这两件事一起看，那个默认关着可能不是偶然。**不作因果断言。**）
4. **TP=4 用了跨拓扑组的设备（`1,2,3,4`）** → ⚠ **只对解码成立**。
   10 KB 上换成 `2,3,4,5` 完全一样（延迟受限）；但 **2560 KB 上差 1.29×、
   10 MB 上组内 vs 跨组差 1.78×**，见 D11 的改正。**别把解码档的结论推广到 prefill。**

### D8 · ragged K 让**常量组**第一次可达，而 asym 量化器在那里是坏的

末组只有 1 个元素时 `mx == mn`，于是 `scale = (mx-mn)/15 = 0`。
`_tiny_where_zero` 把 scale 抬到 bf16-tiny，**但没管 zero**：
`zero = qmin − round(mn/tiny)` ≈ **1e35**，在 bf16 里还是有限值，
一路安静地传到 kernel 的 rank-1 项 `wz * a_ksum`（|a_ksum| ~1e5）才在 fp32 里变成 inf。
症状是 K=1025 / K=5121 的输出全是 non-finite，而 lab 门禁**测不到**——
lab harness 的 `w_zero` 是随机生成在 [-8,7] 的，不是从数据算的。

修法（`fakequant_lab/quant.py`）：常量组用 `scale = |v|/qmax, zero = 0`，对常量组是**精确**的
（`q = ±qmax`，dequant 还原 v）。已验证：
- 非退化组（gl=1024/512/128/33）与修改前**逐位相同** ⇒ **P2 的数字不受影响**；
- 常量组 v ∈ {0.02, −0.7, 0, 3.5} 全部有限且精确。

**教训：一个"防护"只护住了公式的一半，比没有防护更危险**——它把 0 变成 tiny，
让后面那个必然溢出的除法看起来是合法的。写 guard 时要问：**这个退化输入会流到哪几个
输出？** 另外：**lab 门禁自己造的输入分布，可能恰好绕过真实管线才会踩的退化情形**
（这里是 w_zero），所以 torch 侧的 seam 测试不是重复劳动。

### D7 · 继承自 P6、仍然成立的两条

1. **决定性的对照是跟别人比**（`P6_TP.md` D6）：mg 跟自己比只能得出"变贵了"，
   推不出决策。三方对照（mg / pc / w8）才立得住。§2 第 3 项照此办理。
2. **引擎级噪声带 ±15%**（`P6_TP.md` D11）：小于 5% 的单点差异不作数，
   比值不能抵消漂移。
